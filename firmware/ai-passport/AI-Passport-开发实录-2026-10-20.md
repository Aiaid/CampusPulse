### 开工先看这里

**判据已经不是"排除法"了。** 2026-10-21 中午整体反转，理由见 §5.34。

| 项 | 当前值 |
|---|---|
| **车数判据** | **默认不计**。只有命中 `EVID_POSITIVE`（车厂品牌名，`veh_rules.c: VEHICLE_BRANDS[]`）才算 |
| 证据位（低 4 位） | `EVID_LINK_SHORT`(0x08) 仍要勾，但只是**必要条件之一**；0x01/0x02/0x04 都已废弃或 0 命中 |
| 排除标记（高 4 位） | `0x10` Appearance 是手表/电脑/HID/传感器 · `0x40` Fast Pair · `0x80` 已知外设 UUID（`FDF7` HP / `FD92` 小米 / `FEBE` Bose） |
| 在场门槛 | `SCAN_VEHICLE_DWELL_MS` = **10 秒** |
| 表容量 | 384 槽 × **68 字节** = 26 KB；累计表 256 台 × 44 字节 |
| 内存水位 | heap free ≈ **97 KB** / min ≈ **94 KB**（**LVGL 时代的旧值**；直绘后没有 24KB LVGL 池和渲染任务，实际更宽裕，待重测。无 PSRAM，加缓冲要谨慎） |
| 实测效果 | **室内 0 台**（反转前 3~6 台假车），另有 `?3` 疑似；**车棚自反转后未复测** |

### 上次会话（10-21）到底做了什么

细节都在 §5.26~§5.35，这里只留结论：

1. **修掉累计表永远存不进 NVS**（`ESP_ERR_NVS_NOT_ENOUGH_SPACE`）：11 KB blob 在 24 KB
   分区里做"写新+留旧"，峰值刚好占满 6 页 → 改成先擦后写。**顺带查出烧 full.bin 会用
   0xFF 覆盖 NVS 分区**（`0x9000~0x10000`），所以日常只烧 app 段。
2. **判据反转**（v34）：从"默认是车、逐条排除"改成"默认不是车、车厂名准入"。
   排除法是无穷集合，补 6 轮没收敛；车厂是有限集合。
3. **按功能拆模块**（v29）：`ad_parse` / `dev_phone` / `veh_rules` / `dev_diag` /
   `scan_table`，其中 `ad_parse` 是全工程唯一的 AD 遍历入口（原来有四份）。
4. **标定手段从"猜"变成"问固件"**：新增 `[BIKE]` / `[BIKE?]` 日志，LOG ON 时每 5 秒
   逐台打印当前被计入的车。
5. **三件工具**（见 §8）：`analyze_sniff.py` 离线回放、`sniff_wait.py` 等人开 LOG ON、
   `capture_log.py` 抓串口。

## 2. 架构

```
┌────────────────────────────────────────────────────┐
│ page_radar.c   直绘页面（独立任务 / 400ms 节拍）       │
│  ui_mini.c     ui_render/ui_fill/ui_text/ui_digits  │
└──────────────┬─────────────────────────────────────┘
               │ scan_ble_snapshot()  拷一份，不共享指针
┌──────────────▼─────────────────────────────────────┐
│ scan_ble.c     NimBLE Observer + 互斥锁              │
│                on_disc() 只做"解析 + 写表"           │
└──────────────┬─────────────────────────────────────┘
               │ scan_table_observe_classified()
┌──────────────▼─────────────────────────────────────┐
│ scan_table.c   在场表（384 槽 × 68B，零动态分配）      │
│ ad_parse.c     **唯一** AD 遍历入口（纯解析）          │
│ dev_phone.c    手机 / 外设识别（纯函数）              │
│ veh_rules.c    车判据（纯函数，**唯一入口**）          │
│ dev_diag.c     一行诊断文本（同时读上面两家）          │
└────────────────────────────────────────────────────┘
```

**分层的关键理由**：`ad_parse` / `dev_phone` / `veh_rules` 都不碰 NimBLE / LVGL /
FreeRTOS，所以能脱离硬件验证（Python 参考实现 + 离线回放，见 §8 的
`analyze_sniff.py`）。这条设计救过多次。

**`veh_rules_hard_ok()` 只收基本类型**，不收 `scan_entry_t`：

```c
bool veh_rules_hard_ok(bool is_phone, bool is_peripheral, bool connectable,
                       uint8_t evidence, uint16_t manu_id);
```

这样"存表的模块"和"判车的模块"互不认识，判据可以脱离 384 槽的表单独测。

### 时间窗口（当前值）

| 常量 | 值 | 用途 |
|---|---|---|
| `SCAN_LIVE_WINDOW_MS` | **10000** | 在场判定（实测 P90 广播间隔 4 秒，窗口太短会周期掉出）|
| `SCAN_SHORT_WINDOW_MS` | 2000 | 瞬时变化检测 |
| `SCAN_ACTIVE_WINDOW_MS` | 15000 | 唤醒判定专用 |
| `SCAN_VEHICLE_DWELL_MS` | **10000** | 电动车累计在场门槛（原 30 秒，走路采集凑不够）|
| `SCAN_FP_MERGE_WINDOW_MS` | 5000 | 指纹合并窗口，**必须比在场窗口短**，否则同型号设备会被误合并 |

### 3.1 主动扫描 + 关掉控制器去重

```c
params.itvl = SCAN_ITF_INTERVAL_MS * 1000 / 625;   // BLE 时间单位 0.625ms
params.window = SCAN_ITF_WINDOW_MS * 1000 / 625;
params.filter_duplicates = 0;   // 关键
params.passive = 0;             // 主动扫描，SCAN_RSP 里才有名字和厂商数据
```

**为什么 `filter_duplicates` 必须是 0**：控制器级按地址去重后，同一设备后续包里的
**名字永远收不到**——只能拿到第一包。这个 bug 不会报错，只会让界面永远显示空名字。
代价用 host 侧 `DUP_GATE_MS = 2500` 吸收。

### 3.2 手机判定（严格模式）

```c
bool scan_class_is_phone(const scan_facts_t *f)
{
    if (f->has_appearance && f->appearance == APPEARANCE_GENERIC_PHONE) return true;

    if (f->has_manu) {
        if (f->manu_id == MANU_GOOGLE || f->manu_id == MANU_SAMSUNG) {
            if (!name_contains_ci(f->name, f->name_len, "buds") &&
                !name_contains_ci(f->name, f->name_len, "watch") &&
                !name_contains_ci(f->name, f->name_len, "band")) return true;
        }
        // Apple 必须看 Continuity 子类型，不能只看厂商 ID
        if (f->manu_id == MANU_APPLE) return apple_subtype_is_phone(f->apple_subtype);
    }

    // 名字兜底必须先排外设
    if (name_looks_like_phone(f) && !name_looks_like_peripheral(f)) return true;
    return false;
}
```

Apple Continuity 子类型的判定表：

| 子类型 | 含义 | 算手机？ |
|---|---|---|
| `0x01` / `0x07` | AirPods | ✗ |
| `0x05` | AirDrop（Mac 也发） | ✗ |
| `0x09` | AirPlay | ✗ |
| `0x0A` | Watch | ✗ |
| `0x0C` | Handoff | ✓ iPhone 独占 |
| `0x0F` | Nearby Info | ✓ |
| `0x10` | Nearby Action | ✓ |

**这一条就是"严格"的落点**：不按厂商 ID 一刀切，而是看子类型。

### 3.3 电动车判定 —— 排除条件焊死在最内层

```c
bool scan_class_is_vehicle(const scan_facts_t *f, uint8_t evidence_mask,
                           uint32_t dwell_ms, bool connectable)
{
    if (evidence_mask == 0) return false;

    // 硬排除一：是手机就绝不是车。必须在函数内部。
    if (scan_class_is_phone(f)) return false;

    // 硬排除二：明显是外设，无论命中什么证据都不算车。
    if (scan_class_is_peripheral(f)) return false;

    if (dwell_ms < SCAN_VEHICLE_DWELL_MS) return false;
    if (connectable) return false;

    return (scan_class_evidence(f) & evidence_mask) != 0;
}
```

> **这条注释值一个 bug**：iPhone 的 Apple 厂商数据长度经常 ≥ 8，天然命中证据 B。
> 只要"是手机就不算车"的排除写在**调用方外层**，任何别的模块直接调这个函数就会漏。

### 3.4 证据 ABC

| 位 | 证据 | 依据 | 实际强度 |
|---|---|---|---|
| A `0x01` | 私有 128 位 UUID | 车厂传车架号/电量，几乎必带；外设只用 16 位 | **强**，假阳性低 |
| B `0x02` | 厂商数据 ≥ 8 字节 | 车机常发长数据 | **弱**，见 §6 |
| C `0x04` | Appearance ∈ 0x0300~0x03FF | 规范定义为 Vehicle | 强但覆盖率极低 |

负向排除（优先于所有证据）：HID 外观 0x03C0~0x03C4、HID/FastPair UUID、
名字含 mouse/keyboard/buds/watch 等。

### 3.5 真实进度倒计时（v8）

```c
// 不再"改动时刻 + 30 秒"写死，而是问表：最接近达标的候选还差多久
out->vehicle_wait_ms = scan_table_next_vehicle_wait_ms(&s_table, t, s_evidence_mask);
```

```c
uint32_t scan_table_next_vehicle_wait_ms(...)
{
    if (evidence_mask == 0) return 0;
    for (每个在场候选) {
        if (已达标的) return 0;                       // 不用等
        need = SCAN_VEHICLE_DWELL_MS - e->dwell_ms;   // 真实缺口
        min_need = min(min_need, need);
    }
    return have_candidate ? min_need : 0;
}
```

```
│ ──────────────────────   │  分隔线
│ ▓ [■] 手机采样            │  焦点行：左侧黄条 + 深底带
│   [■] 电动车采样          │
│   全部清零                │  两段确认（第二段文字变红）
│ ▲▼ 选择  OK 切换  长按 关机│  底部提示，随状态变
└──────────────────────────┘
```

### 按键

| 键 | 作用 |
|---|---|
| UP / DOWN | 焦点在"无 → 手机采样 → 电动车采样 → 全部清零"之间移动；**只移动，不改判据** |
| OK 短按 | 切换当前行的勾选；焦点在"无"时先落到"手机采样" |
| OK 双击 | 开关串口标定日志 `LOG ON`（标题栏出现 `LOG`） |
| OK 长按 | **关机进深睡**（⚠ 与旧版"回菜单"不同，见 §5.35 ④） |

### 与旧版的四处有意差异

1. **RESET 改成两段确认**：再按一次才清零，UP/DOWN 或 3 秒超时取消。
   理由：误清空的代价是车数要重新观察 10 秒。
2. **诊断行（APPLE/GOOGLE、LIVE/RAW）不进界面**：它是标定工具，串口日志保留。
   ⚠ 副作用：`vehicle_maybe`（疑似数）也因此没地方显示，见 §5.35 ③。
3. **数字区平滑不变**：5 帧中位数；判据切换/清零时必须 `smooth_reset`，
   否则新旧数字混出怪值。
4. **`--` 而不是 `0`**：PHONE 关掉、车数在观察期、判据关掉，都显示 `--`
   （没在看 ≠ 没有人）。

## 5. 踩的坑（核心章节）

### 5.1 两个真 bug —— 被 PC 侧断言抓到

**坑一：`Pixel Buds` 被判成手机。**

Google 厂商 ID 那一层已经因为名字含 "buds" 排除了，但紧接着的**名字兜底**
又因为含 "pixel" 命中手机关键词——白排了。

修复：

```c
if (name_looks_like_phone(f) && !name_looks_like_peripheral(f)) return true;
```

> 教训：**同一份判定里，"先排除"和"再兜底"必须互相检查**。中间夹一个不看前序结论的
> 兜底分支，前面的排除就白做了。

**坑二：`iPhone` 被判成电动车（更严重）。**

iPhone 的 Apple 厂商数据常 ≥ 8 字节 → 天然命中证据 B；"是手机就不算车"的排除
写在 `scan_table_count_vehicle` 外层，`scan_class_is_vehicle` 本身不查。

修复：把它焊死进 `scan_class_is_vehicle` 内部。

> 教训：**安全相关的排除条件要放最内层判定函数，不能指望调用方记得先排一遍。**

### 5.2 v6 → v7：我自己把页面改成了"卡死"

用户反馈「按什么都没用了」。真相是**程序没崩，是我加的色块把文字全遮住了**。

**根因**：LVGL 里同级对象**后创建的盖在上面**。v6 的循环是：

```
第1轮：建 A 色块 → 建 A 文字   （OK）
第2轮：建 B 色块 → 盖住 A 文字
第3轮：建 C 色块 → 盖住 A/B 文字
最后：焦点落回 A 行，A 的色块又压住 A 自己的文字
```

用户看到的是"文字全没了 / 页面死机"，实际上焦点一直在正常跳动。

**第二个错误**：把焦点行文字改成白色压在红底上，于是 `[x]` / `[ ]` 读不出来——
**把"焦点"和"勾选"两个维度合成一个了**，等于倒退。

**修法**：
- 三块色块 → **一块** `s_ev_hl`，按焦点行改 `lv_obj_set_y()`；且**在循环外、文字之前创建**。
- 底色换 `UI_INK` 深色带 + 行首 `>`，**不动文字颜色**。

> 教训一：LVGL 的 z 序 = 创建顺序。凡是"背景 + 前景"的组合，背景必须先建。
> 教训二：**两个语义维度（在哪 / 开没开）不能被同一个视觉通道承载。**

### 5.3 v8：证据 B 是个假证据

用户：「我在 10 楼，难不成真的有 27 辆电动车？」

三个机制，按贡献排序：

**① 证据 B 几乎等于没有约束。**
一台 iPhone 的普通 Continuity 广播，厂商数据经常就是 10~15 字节；
Windows Surface 中继、安卓快速配对也都超 8 字节。
所以「厂商数据 ≥ 8 字节」在现实里的实际含义是「**只要不是外设就算车**」。

**② 楼板挡不住 2.4GHz 多少。**
一层混凝土楼板 10~20 dB。10 楼离窗 5m、楼下 30m、一层楼板，合计 40~60 dB。
理论路径损耗（2.4 GHz，含发射功率假设）：

| 距离 | 自由空间 RSSI |
|---|---|
| 1 m | ≈ -80 dBm |
| 3 m | ≈ -70 dBm |
| 10 m | ≈ -60 dBm |
| 30 m | ≈ -50 dBm |

所以楼下路边的车完全可能被收进来。

**③ 一辆车可能多条链路**（中控 / BMS / 仪表各发一条）。广播内容上区分不了，
目前无解，只能靠 RSSI 相近 + 广播间隔一致做统计推断——还没做。

> 教训：**一个判定规则的"名字"和它的"实际效果"经常不是一回事。**
> 「厂商数据 ≥ 8 字节」听起来是在筛"数据丰富的车机"，
> 实际是在筛"所有不发短数据的设备"。**规则写出来之后，必须反推它在真实世界里
> 会放进来什么**，而不是相信命名。
>
> 更要紧的：这个数据是用户报的，不是我测出来的。
> **早一点拿真实场景的荒谬数据去撞一次，能省掉七轮迭代。**

### 5.4 构建环境的坑（Windows + ESP-IDF）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | `idf.py: command not found` | Git Bash 里 `export.sh` 无效 | 改用 PowerShell 工具 |
| 2 | `"cmake" must be available on the PATH` | 工具在带版本号的子目录里 | 手拼全量 PATH，**每段都带版本号** |

| 7 | 改了源码但 ninja 不重编 | `& idf.py` 受 PATHEXT 影响实际没跑，却 exit 0 | 比对 `.ninja_log` 里 obj 时间戳 vs 源文件 mtime |
| 8 | 删 obj 强制重编报 `Permission denied` | 残留 ninja.exe/cmake.exe 抢文件 | 先 `Stop-Process` 全部 ninja/cmake |

### 5.6 硬件/固件层面

```python
segs = [(0x0, "bootloader.bin"), (0x8000, "partition-table.bin"), (0x10000, "app.bin")]
data = b""
for off, p in segs:
```

### 5.8 键位：我擅自发明了一套和套件不一致的操作

用户反馈：「你的按键逻辑没有保持套件原有的逻辑，改一下，不让无法退出应用」。

**套件原有约定**（`main.c` 的菜单页 + `demo_navigation.c`）：

```
UP    -> 选项上移
DOWN  -> 选项下移
OK    -> 确认 / 进入
长按  -> 退出（回到上一层）
```

`demo_navigation_handle()` 里写得清清楚楚：

```c
if (navigation->active >= 0) {
    result.action = input == DEMO_NAV_INPUT_OK_LONG
                  ? DEMO_NAV_ACTION_EXIT : DEMO_NAV_ACTION_FORWARD;
    return result;
}
```

**我改成了什么**：OK = 焦点下移、UP = 焦点上移、DOWN = 切换勾选。

问题有两层：

1. **手感割裂**。同一个设备上，菜单页是"上下选、OK 进"，进了 Dev Seen 突然变成
   "OK 也在选、DOWN 在改值"——用户每次进这个页面都要重新学一遍键位。
2. **退出靠运气**。退出走的是"OK 长按"，而我让 OK 短按也承担了移动焦点的职责，
   于是同一颗键在不同按法下语义完全不连续：短按移动、长按退出、双击开日志。
   用户不确定自己的按法会被算成哪一种，就**不敢按**——表现出来就是"退不出去"。

**改回套件约定**：

| 键 | 现在 |
|---|---|
| UP | 焦点上移（A→无→C→B→A） |
| DOWN | 焦点下移（无→A→B→C→无） |
| OK 短按 | 勾选/取消当前焦点行；焦点在"无"时先落到 A 行，不顺手改 |
| OK 双击 | 开关日志 |
| OK 长按 | 回菜单（`main.c` 处理，本页不参与） |

方向键**只移动、永不改判据**——手滑按两下只是光标来回走，不会悄悄改掉一条证据
再让你等 30 秒。要改，必须按 OK。

> 教训：**页面级的交互设计必须先服从设备级的约定。**
> 一个功能页可以有自己的内部规则（比如"焦点还要经过一个空位"），
> 但**按键到动作的映射不能和宿主的导航层打架**。
> 尤其是"退出"这种兜底操作：它必须是最短、最确定、最不容混淆的那条路径。
> 让同一颗键同时兼"移动"和"退出"，等于把用户关在页面里。

### 5.9 v10：改判据后车数不归零 —— v8 顺手删掉的一个调用

**现象**：屏幕上已经有车数了，进选项里改勾选，车数**不归 0**，也不出现 `LOADING`。
用户唯一能判断"按键生效了没有"的线索没了——数字没动，到底是判据改了但结论一样，
还是按键根本没吃进去？

**根因一句话**：`scan_ble_set_evidence()` 里那句

```c
scan_table_restart_vehicle_timer(&s_table, t);   // 改判据 → 全体在场计时归零
```

**被删了**。而 v8 那轮改动（做"真实进度倒计时"）顺手把注释也改成了
「这里**不再**重置所有设备的 dwell」，理由是"现场设备早就在场几百秒，那 30 秒是凭空发明的等待"。

**两个信号说明这是漏改、不是有意设计**：

1. `scan_table_restart_vehicle_timer()` **函数本体一直在**，头文件注释还写着
   「什么时候调用：用户改动了证据勾选之后」。实现里的注释把调用否掉了，
   头文件里的注释还留着——**两份注释互相打脸**。
2. 那个函数是**死代码**：全工程只有它自己的定义，没有任何调用点。
   编译器不会提醒你——`-Wunused-function` 只管 `static` 函数，
   导出的非 static 函数"没人调用"是完全合法的。

**为什么"不重置"看起来更聪明，实际是错的**：

v8 的推理是"设备在不在，跟判据无关；换判据不需要重新观察它们在不在，所以立刻算是对的"。
前半句对，后半句漏了一层：**车数不是"设备在不在"，而是"这台设备在新判据下被判成什么"**。
旧判据下攒的那 30 秒，是给旧判据做担保的；新判据一来，担保就失效了。
不归零的后果是数字在**一帧之内**跳变，用户看不到任何过程。

**第二个坑：`wait_ms == 0` 有两个含义。**

`scan_table_next_vehicle_wait_ms()`：

- 返回 0 = 已经有设备达标 → 现在就是结果
- 返回 0 = **现场根本没有候选设备** → 也是现在就是结果

界面原来用 `vehicle_wait_ms > 0` 当"是否该显示倒计时"的开关。一改判据、现场又没候选，
这个开关立刻是 0，界面从数字直接跳回 `TOTAL`，看着像什么都没发生。
所以修的时候没有复用这个字段，而是新加了一个由**事件**驱动的状态：

```c
// scan_ble.c：判据变化（或本机刚启动）之后的 30 秒就是观察期
// 注意它不看"有没有候选"——观察期由"判据刚变"这个事件决定，不由数据决定。
const uint32_t since = (uint32_t)(now_ms() - s_evidence_set_ms);
if (mask != 0 && since < SCAN_VEHICLE_DWELL_MS) {
    out->vehicle_settle_left_ms = SCAN_VEHICLE_DWELL_MS - since;
}
```

界面据此分两档：

| 状态 | 车数 | 状态行 |
|---|---|---|
| `vehicle_settle_left_ms > 0` | `--` | `LOADING Ns` |
| 观察期结束、`vehicle_wait_ms > 0` | 真实车数 | `WAIT Ns`（有新候选在攒） |

`--` 和 `0` 必须分开：`--` 是"还没有结论"，`0` 是"看过了，确实没有"。
原来两者都用 `0` 表达，用户没法区分"功能刚重置"和"真的没车"。

**第三个坑：重置得有边界。**

`scan_table_restart_vehicle_timer()` 只动 `dwell_base_ms` / `dwell_ms`，
不碰 `evidence` / `cls` / `peripheral`：

- `evidence`、`cls`、`peripheral` 是**设备的固有属性**，换判据不需要重新观察；
- 只有"在场多久"是**观察结论**，必须重来。

一把 `memset` 清干净会顺手把手机判定也清掉，手机数跟着跳一次——那是另一个 bug。

**改完顺手加的断言**（`tests/scan_table_ref.py`、`tests/test_scan_table.c`）：

```
在场 40s → 车数 1、不等待
改判据   → 车数 0、wait = 30000   ← 旧结论作废
再 10s   → 车数 0、wait = 20000   ← 倒计时按真实进度走
再 20s   → 车数 1、wait = 0       ← 重新出数
mask=0   → 车数 0、wait = 0       ← 是"关闭"，不是"等待"
```

> 教训一：**删一个调用的时候，顺手改掉的注释就是未来的谎言。**
> 这次是调用点、实现注释、头文件注释三处不一致，靠 grep 函数名一眼看出来——
> 所以"改完顺手 grep 一下这个函数还有谁在用"值得成为习惯。
>
> 教训二：**一个返回值承担两种语义，UI 就必然在某个分支上读错。**
> `0` 既表示"不用等"也表示"没得等"，区别只在数据里，不在返回值里。
> 涉及"能不能显示"的判断，宁可多给一个字段，也不要去解释一个含糊的 0。
>
> 教训三：**用户报"没反应"的时候，先问"有没有反馈通道"。**
> v8 那轮把 30 秒等待当成"多余的延时"砍掉，砍掉的其实是唯一的反馈信号。
> 一个改动如果用户在屏幕上看不出来，那就等于没做。

### 5.10 v11：随便按两下卡死 —— 这一页从来没给 LVGL 加锁

**现象**：上一版修完判据切换，按两下就"卡死、动不了"。**不是屏幕不刷新，是任务死了。**

**定位顺序（值得背下来）**：

1. 抓串口。看到：

```
E (288494) task_wdt: Task watchdog got triggered.
E (288494) task_wdt:  - IDLE (CPU 0)
E (288494) task_wdt: CPU 0: demo_input
E (288494) task_wdt: Print CPU 0 (current core) registers
MEPC    : 0x42046c1a  RA : 0x42046c0c
```

到这一步就能排除"界面没画"——是 `demo_input` 任务卡死了，IDLE 喂不到狗。

2. `addr2line`：

```bash
xtensa-esp32-elf-addr2line.exe -pfiaC -e build/FoloToy-AI-Passport.elf 0x42046c1a
# -> lv_inv_area at lv_refr.c:286
```

3. 打开 `lv_refr.c:275` 读那段注释和断言：

```c
/**
 * There are two reasons for this issue:
 *  1.LVGL API is being used across threads, such as modifying widget properties
 *    in another thread or within an interrupt handler during the main thread
 *    rendering process.
 *  2.User-customized widget modify widget properties/styles again within the DRAW event.
 */
LV_ASSERT_MSG(!disp->rendering_in_progress,
              "Invalidate area is not allowed during rendering.");
```

**LVGL 把诊断结论直接写在源码里了。** 默认的 assert handler 是 `while(1)`，
所以命中的表现是"任务死循环 + 看门狗"，不是崩溃重启。

**根因**：`demo_scan.c` 的 `refresh()` 是从 `demo_input` 任务里调的，
但 LVGL 有自己的 `lv_timer_handler` 任务（启动日志里那行 `LVGL: Starting LVGL task`）。
两个任务同时动 LVGL 对象 → 一撞就是这条断言。

工程里**其他每个 demo 都加了锁**：`demo_button.c` / `demo_display.c` / `demo_audio.c` /
`demo_low_power.c` / `demo_wifi.c` / `main.c` 的导航层，清一色

```c
if (!bsp_lvgl_lock(250)) return;
... LVGL 调用 ...
bsp_lvgl_unlock();
```

**只有 `demo_scan.c` 一行都没有。** 这是我写这个页面时的漏项——而且它是从 v1 就漏的，
一直侥幸没炸（`lv_label_set_text_fmt` 内容大部分时间不变，LVGL 会提前返回，很少真的 invalidate）。

**为什么 v10 一改就必炸**：

1. `scan_ble_set_evidence()` 为了原子的拿表锁，加了最长 200ms 的等待。
   于是 `refresh()` 的执行时刻被推后，**撞上渲染窗口的概率大幅上升**。
2. 车数在 `"--"` 和数字之间切换，每次都要 realloc label 的文本缓冲 →
   每次都真的触发 invalidate。原来"文本没变就跳过"的护身符失效了。

两个改动都不算错，只是把潜伏的雷踩响了。

**修法**：

```c
static void refresh(void)
{
    // 递归锁：LVGL 任务里的 tick() 再取一次不会自锁
    if (!bsp_lvgl_lock(250)) return;
    scan_ble_snapshot(&s_snap);   // s_snap 是共享静态缓冲，也必须进锁
    ... 全部 LVGL 调用 ...
    bsp_lvgl_unlock();
}
```

`demo_scan_enter()` / `demo_scan_exit()` 不用加：`main.c` 的 `process_input()`
在 `ENTER` / `EXIT` 两个分支里已经持锁（`demo->enter()` 是在锁内调的）。
`key()` 那个分支**不持锁**，所以每个页面的 `key` 自己负责——这就是为什么
`demo_button_key` 里也有一对 lock/unlock。

> 教训一：**新页面要先抄骨架，不是先抄逻辑。**
> 这个页面的键位、布局、判据都照着套件约定写对了，唯独漏了"跨任务碰 LVGL 要加锁"
> 这条**看不见的契约**。它不在任何头文件里，只在别的 demo 的代码里。
> 写新页面的第一步应该是 `grep bsp_lvgl_lock main/*.c`，看清楚谁在哪个任务里被调。
>
> 教训二：**"卡死"先分清三种：界面不刷新 / 任务死循环 / 芯片重启。**
> 串口一行 `task_wdt ... CPU 0: <任务名>` 就能定性，配一次 `addr2line` 就落到源码行。
> 这次没有花一秒钟猜 UI，是因为第一步就去读了串口。
> （对照 §5.2 那次"卡死"——那次是真·显示问题，串口安静、`focus` 日志正常跳动，
> 两次现象的串口特征完全不同，这才是最快的区分手段。）
>
> 教训三：**改一个"看起来无害"的等待时间，可能把别处的竞态踩响。**
> 200ms 的拿锁等待本身是对的，但它改变了 refresh 的执行相位。
> 改时序的时候要问一句：这个函数还在别的任务里被调用吗？

### 5.11 v12：一个人站在电梯里，手机数是 0

**现象**：电梯里只有用户一个人，反复开关手机蓝牙，`PHONE` 一直是 0。

**我第一轮猜错了。** 看到「开关蓝牙都没反应」，我先按 iPhone 的逻辑推：
`DUP_GATE_MS` 按 MAC 去重 → 每台设备只被采到一种 Continuity 子类型 →
抽到 `0x09`/`0x12` 就不算手机。这条推理本身没错，日志也确实支持
（82 台 Apple 设备里只有 1 台见过两种载荷，30 台被判成手机）。

**但用户一句「我手机不是 iPhone」，整条推理作废。** 那个 63% 的抽签概率
对安卓根本不成立。

**重来，看厂商 ID。** 给串口日志加两个只读字段（`sub=` / `phone=`，
只影响 `LOG ON` 输出，不动判定），重新抓 12 秒：

| 厂商 ID | 包数 | 设备数 | 备注 |
|---|---|---|---|
| `0x0006` 微软 | 1435 | 32 | Windows 附近共享 |
| `0x004C` 苹果 | 1214 | 70 | 其中 30 台判成手机 |
| **`0x0837`** | 89 | 2 | **RSSI -28 dBm**，`phone=0` |
| `0x0823` / `0x027D` 华为 / `0x0802` / `0xCC12` / `0xB822` / `0x07E0` | 268 | 16 | 全部 `phone=0` |

`0x00E0`（Google）和 `0x0075`（Samsung）**一次都没出现**。

`RSSI -28 dBm` 是贴着设备的距离，只可能是用户自己的手机在广播。查
Bluetooth SIG 的厂商 ID 列表：

> `0x0837  vivo Mobile Communication Co., Ltd.`

**答案就是这一行**：白名单只写了 Apple / Google / Samsung 三家，
vivo 不在里面。手机在广播、包被完整收到（89 包、27 字节厂商数据），
然后被判成 `unknown`。

**这个 bug 一次造成两个错**：vivo 手机既不计入手机数，又因为
`manu_len = 25 ≥ 8` 命中证据 B，**被算进了电动车数**。
`0x027D` 华为、`0x0823`、`0x0802` 全都带着 `ev=0x02`——
10 楼那 27 辆车里，有一部分就是这么来的。

**修的时候又踩了 §5.1 那个老坑**：

厂商分支已经加了 `"tws"` 排除，但紧接着的**名字兜底**又把
`"vivo TWS 3e"` 捞了回来（它含品牌词 `vivo`）。新加的断言当场抓到：

```
AssertionError: vivo TWS 不能被算成手机
```

修法是把 `tws` 也塞进 `name_looks_like_peripheral()` 的关键词表——
**"先排除"的关键词必须覆盖"再兜底"的关键词**，否则中间那条兜底会把排除白做。
和 §5.1 的 `Pixel Buds` 是同一个形态，这是第二次。

**但更要紧的是一个方法论问题，得说出来**：

BLE 广播里**没有"我是手机"这个字段**。厂商 ID 只能说明品牌，
说明不了"这是手机还是耳机还是电视"——同一家既做手机也做 TWS。
而且很多安卓机型**默认根本不发可被发现的广播**（蓝牙开着但不可见），
连包都收不到。

所以这个指标在中国这个安卓为主的环境里，本质上等于 **"iPhone 数"**。
办公室能数出 30，是因为苹果设备多；换到安卓为主的场景会塌成个位数。

> 教训一：**用户给的一个前提错了，整条推理链都要作废重来，不能打补丁。**
> 这次是"我以为他用 iPhone"。他纠正之后，正确的做法不是"那安卓可能也这样"，
> 而是回到最原始的数据重新看——一问厂商 ID，答案立刻就在日志里躺着。
>
> 教训二：**白名单是维护性债务。** 每加一家厂商就要重新验一遍误判率，
> 而且永远覆盖不完（华为、小米、OPPO、荣耀、一加、realme……）。
> 短期可以加，长期要么改用 Wi-Fi 探针帧数手机，要么干脆不用"手机数"这个口径。
>
> 教训三：**同一个判定漏洞会同时污染两个指标。** 手机漏判 → 设备落到"未知"桶
> → 证据 B 一捞 → 变成电动车。看到"车数偏高"时，先看诊断行里
> `unknown` 的构成，别只盯着 `APPLE`。

**后续**：白名单从 3 家扩到 11 家（华为 `0x027D`、荣耀 `0x09C6`、小米 `0x038F`、
OPPO `0x079A`、一加 `0x072F`、realme `0x08A4`、魅族 `0x03AB`、努比亚 `0x08CA`、
联想 `0x02C5`、摩托 `0x0008`）。

每条都查过 Bluetooth SIG 列表，**没有一条是凭记忆填的**。查表这一步省不掉：

> `0x0157` 看上去像小米（早期小米手环确实有一堆设备用这个段），
> 但官方列表里它是 **Anhui Huami（华米）**，小米是 `0x038F`。

填错不会报错、不会崩，只会让一堆 Amazfit 手表变成人、而小米手机一个也数不到。
所以断言里专门钉了一条：`0x0157` 必须判成"不是手机"。**把踩过的坑写成断言，
比写在注释里可靠。**

但要说清楚：**扩白名单提高的是召回，代价是精度**。同厂的智能手表、手环、
路由如果没带 `watch`/`band` 这类名字，一样会被算成手机。手机带名字的比例很低、
配件带名字的比例很高——这条判据**只能靠这个不对称性赌**，不是真判据。

### 5.13 v13：把"在场"改成带滞回的状态机

**这个方案是用户提的，不是我想到的。** 原话：

> 进入计数：3~5 秒窗口内同一地址命中 ≥3 次，且 RSSI 中位数 ≥ -85 dBm；
> 退出计数：连续 3~5 个扫描周期未检测到，或 RSSI 中位数 < -90 dBm；
> TTL 兜底：超过 8~12 秒无更新自动过期。

我先前那版只做了"连续 3 个采样周期"——**没有 RSSI 维度，也没有滞回**。
在 -85 附近徘徊的设备照样来回翻。用户这三条把问题补全了。

**实测依据**（教室，120 台设备、223 包/秒）：

| 指标 | 数值 |
|---|---|
| 低于 -80 dBm 的包 | **43%** |
| 10 秒内只出现 1~2 包的设备 | **33 台** |
| 唯一 MAC 数 | 120 |

这 33 台就是抖动的来源：它们随时掉出窗口，数字因此上下跳。

**实现：一个字节同时表达两个条件。**

```c
uint8_t gate_bits;      // bit0 = 本秒收到，bit1 = 上一秒……
uint32_t gate_last_ms;  // 位图相位基准
```

于是：

```c
窗口内命中几次  = popcount8(bits & ((1<<5)-1))     // 5 秒窗口
连续 4 秒没收到 = (bits & ((1<<4)-1)) == 0
```

不需要两个计数器、不需要时间戳数组。每槽新增约 13 字节，128 槽 ≈ 1.7 KB。

**进入 / 退出**：

```c
if (!counted) {
    if (popcount8(bits & win_mask) >= 3 && median_rssi >= -85) counted = true;
} else {
    if ((bits & miss_mask) == 0 || median_rssi < -90) { counted = false; bits = 0; }
}
```

退出时把位图清零是刻意的：**重新进入必须重新攒满 3 格**，不继承上一轮命中。

**RSSI 用中位数**（最近 5 次插入排序）：瞬时值会被单包遮挡带偏 20dB，
平均值会被一个 -20dB 的异常拉偏 4dB，中位数完全不受单包影响，正好配滞回。

**踩到的一个坑：状态机不能只靠"收到包"驱动。**

第一版 `tick_confirm()` 只在 `on_disc()` 里调。用 Python 复刻验证时发现：

```
进入后停发 → 只有 ENTER，没有 EXIT
```

设备走了就再也没有包，tick 永远不执行，`counted` 永远是 true。
**空旷场景下（最后一台设备离开）数字会僵在屏幕上**——而那恰恰是最需要它降的时候。

修法：在 `scan_ble_snapshot()` 里也调一次。UI 每 400ms 刷一帧，天然是时钟源。
两个调用点都保留（on_disc 保证及时、snapshot 保证兜底），tick 内部按整秒限流，重复调用无害。

**Python 复刻验证的行为**：

| 场景 | 结果 |
|---|---|
| 强信号 -70 稳定 | 3000ms 进入 |
| 弱信号 -88 稳定 | 永不进入（-88 < -85） |
| 强 4 秒后降到 -87 | 保持，不退出（滞回生效） |
| 强 4 秒后跌到 -92 | 5000ms 退出 |
| 进入后停发 | 约 5 秒退出（4 秒判定 + 1 秒采样容差） |

**参数**（全在 `scan_table.h`，改一处即可）：

| 常量 | 值 | 含义 |
|---|---|---|
| `SCAN_GATE_WINDOW_S` | 5 | 进入判定窗口 |
| `SCAN_GATE_ENTER_HITS` | 3 | 窗口内至少命中几秒 |
| `SCAN_GATE_EXIT_MISS_S` | 4 | 连续几秒没收到就退出 |
| `SCAN_GATE_RSSI_ENTER` | -85 | 进入的 RSSI 中位数下限 |
| `SCAN_GATE_RSSI_EXIT` | -90 | 退出阈值（比进入低 5dB，形成死区） |
| `SCAN_TTL_MS` | 10000 | 兜底过期 |
| `SCAN_RSSI_HIST_LEN` | 5 | 中位数窗口 |

连带改动：`prune` 的窗口从 5 秒改成 `SCAN_TTL_MS`。
**条目必须在表里活够 TTL，退出状态机才有机会跑完**——用 5 秒清掉，
条目会在判退出之前就消失，滞回等于没生效。"在不在场"从此由 `counted` 决定，
不再靠条目是否被清掉。

### 5.14 v14：数字为什么一直跳 —— 60 秒日志拆出三个独立来源

用户报「波动仍然能达到 10」。这次不猜，开 `LOG ON` 抓了 **60.2 秒 / 15977 包
（265 包/秒）/ 242 台不同 MAC**，然后写了个模拟器**逐包复刻固件的表行为**，
先预测屏幕数字，再改代码。

#### 三个来源，一个比一个具体

**① 表容量 128 装不下现场 —— 这是主因**

60 秒内出现 242 台设备，而 5 秒窗口内同时在场的约 190 台。
128 个槽根本不够，于是每来一台新的就得淘汰一台"最久未更新"的。

模拟结果：**60 秒内淘汰 2275 次，约 38 次/秒。**
而被淘汰的设备往往只是 3~4 秒没发包（完全正常），下一包来了又插回去。
屏幕上的数字就这样一秒抖好几次。

更难看的是模拟出的 LIVE 序列：**恒等于 128**。不是巧合，是表被钉死在容量上限。
所谓"在场设备数"从 128 往上就再也上不去了。

**② 在场窗口 5 秒短于实际广播间隔**

现场实测的设备级广播间隔：

| 分位 | P50 | P75 | P90 | max |
|---|---|---|---|---|
| 间隔 | 2002ms | 3010ms | 4011ms | 19448ms |

P90 那批设备间隔 4 秒，**只要丢一个包就超过 5 秒**，于是周期性掉出窗口。
这一条与容量无关——模拟里把容量加到 384、淘汰次数归零之后，
手机数峰峰值仍然**正好是 10**；只有把窗口拉到 10 秒才降到 7。

**③ 显示层逐帧直出，没有任何时间维度的平滑**

UI 每 400ms 重画一次，每次都把瞬时值直接写上屏。
设备数在 190 上下摆动 10 台，屏幕上就是 190 和 200 来回跳。

#### 改法

| 改动 | 原值 | 新值 | 依据 |
|---|---|---|---|
| `SCAN_TABLE_CAPACITY` | 128 | **384** | 模拟：淘汰 2275 次 → **0 次**；LIVE 从钉在 128 变成真实值 |
| `SCAN_LIVE_WINDOW_MS` | 5000 | **10000** | 覆盖 P95 左右的真实广播间隔；手机数峰峰 10 → 7 |
| `SCAN_FP_MERGE_WINDOW_MS` | （复用在场窗口） | **5000** | 单独拆出来：窗口放宽后若合并窗口跟着放宽，两台同型号设备会被误合并 |
| 显示层 | 直出 | **5 帧中位数**（2 秒） | 数据抖动是口径的必然，不该让用户逐帧读 |

模拟给出的预测（同一份日志）：

| 配置 | LIVE 均值 | LIVE 峰峰 | PHONE 均值 | PHONE 峰峰 | 淘汰次数 |
|---|---|---|---|---|---|
| 原：128 槽 5s | 128.0 | 0（钉死） | 76.6 | **10** | **2275** |
| 384 槽 5s | 189.0 | 16 | 90.4 | 10 | 0 |
| 384 槽 10s | 210.1 | 13 | 95.6 | **7** | 0 |
| 384 槽 15s | 217.3 | 11 | 99.0 | 7 | 0 |

窗口拉到 15 秒后峰峰不再下降（还是 7），说明剩下的部分是设备真的进出，
再放宽只会让数字虚高——所以停在 10 秒。

#### 内存

每项 68 字节，384 项 = **26KB**。旧注释写着"每项约 24 字节，128 项约 3KB"，
**这个数字早就过时了**（结构体加了 RSSI 历史、gate 位图、分类缓存之后就从 24 涨到 68）。
按错误注释做容量决策会低估 3 倍。已在注释里改正，并加了启动日志：

```
表: entry=68B x 384 = 26112B, heap free=... min=...
```

#### 教训

- **"数字在跳"要分成三件事查**：容量够不够、窗口合不合适、显示有没有平滑。
  只看其中一层，改完会觉得"没效果"——这也是上一版把窗口改成状态机却更糟的原因。
- **结构体的 sizeof 不能靠注释**。注释写 24、实际 68，差 3 倍，而编译器不会提醒。
  凡是拿大小做容量决策，就去打一次 `sizeof`。
- **模拟器比真机试错快得多**。这次先抓日志、再写模拟器预测、最后才改代码，
  一次就到位。前面几轮"改完烧了再看"的做法，代价是反复烧录和反复失望。

### 5.15 v15：RESET 行 —— 又一个"函数在、调用没了"

用户要在三条证据下面加一个 `reset`，按一次清空手机数和电动车数。

翻代码时发现 **`scan_ble_reset()` 早就写好了**，头文件里还有一行注释：
「清空计数表，重新开始统计（扫描本身不中断）。换场景时按 OK 调用。」

——**注释写着"按 OK 调用"，但界面上从来没有这一行。** 这和 §5.9 那个
`scan_table_restart_vehicle_timer()` 是同一个形态：函数活着、注释写着该被调、
调用点不存在。`-Wunused-function` 管不到它（它是非 static 的公开接口，会导出符号），
所以编译器一个字都不会说。

#### 改了什么

| 项 | 变化 |
|---|---|
| 焦点行数 | 4 → **5**（NONE + A/B/C + RESET） |
| 布局 | 状态行 182→174、诊断行 200→190、证据区 218→208、行距 20→**18** |
| `s_ev_rows` | 3 → **4** 个标签 |
| RESET 行 | **不带 `[ ]`**，橙字。它不是"状态"，是"一次动作"，写成勾选框会让用户以为能取消 |
| 按 OK | 调 `scan_ble_reset()` + 清空三个平滑缓冲 |

布局是被逼出来的：245 像素要塞 5 行，只能把上面的行全往上挪 8px、行距压到 18。
montserrat_14 字高 14px，18 还剩 4px 间隙，不粘连。

#### 为什么不做二次确认

这一页只有三个键。做"再按一次确认"会把焦点锁在一行里，用户不知道怎么退出
那个确认态——这和 v9 那次「擅自发明键位，用户被困在页面里」是同一类风险。
代价也确实小：按错了，手机数 1~2 秒就因为设备还在广播而自己涨回来。

#### 重置后两个数字的行为完全不同（这点必须写清楚，否则会被当成 bug）

| 指标 | 现象 | 原因 |
|---|---|---|
| PHONE | 归 0 后 **1~2 秒涨回** | 手机不要求 dwell，设备还在广播，重新观测到就计入 |
| E-BIKE | 保持 `--` + `LOADING 30s` | 车要求累计在场 30 秒，清表把所有 dwell 一起清了 |

用户很容易把"按了 RESET 手机数马上又变回去"读成"没生效"。**那不是 bug，
是物理事实**——人还站在原地，信号还在空中，扫描器不可能装作看不见。
RESET 清的是**历史累计**，不是"让现场安静下来"。

`scan_ble_reset()` 里顺手更新了 `s_evidence_set_ms`，这一句是关键：
不更新的话车数会立刻显示 0，而那个 0 会被读成"确实没有车"，
实际上只是"还没开始观察"。

#### 教训

- **公开接口比 static 函数更危险**：`static` 没用上还有 `-Wunused-function` 兜底，
  非 static 的死代码连警告都没有。加新界面功能前，先 grep 一遍有没有现成的接口。
- **"动作行"不能画成"勾选行"**。`[ ] RESET` 会让人以为能勾上再取消，
  实际按一次就清空。视觉上必须和状态行区分开。

### 5.16 v16：拿着设备去车棚转一圈 —— 数据在 RAM 里，拔线就没了

用户提了一个新用法：「直接拿这个套件去转一圈，不用接电脑，回来再接电脑」。

这在当时**根本不成立**，两个障碍：

1. 扫描表按 10 秒在场窗口滚动，走回车棚的路程早就过期了；
2. `LOG ON` 的逐包日志是 `ESP_LOG` 写 UART，**没接电脑时没有接收方，直接丢弃**，不缓存。

于是设计了「累计签名表」（`scan_stats.c`）：不按时间过期，只按签名聚合。
第一版按 `(厂商 ID, 设备名前缀)` 分组，48 组。

**但第一次实测就白跑了一趟。** 回来插线，串口 1.5MB 日志里 `[STAT]` 一条都没有，
第一条是：

```
I (98801) BLE_INIT: ...
```

**uptime 只有 98 秒** —— 芯片在插线的瞬间重启过。累计表在 RAM，重启就清零。

> **教训**：我提醒用户"别断电"，却忘了**拔 USB 本身就是断电**。
> 设备靠电池撑不住拔线，所以"离线采集"这个方案在只有 RAM 表的时候是第一版就死的。

修法：落盘到 NVS（`scan_stats_save/load/clear_nvs`，magic + version 校验），
三个时机保存——退出页面（`scan_ble_stop` 末尾）、页面定时器每 30 秒兜底、RESET 时清。

**还埋了一个死角又被自己挖出来**：第一版写成"导出即消费"（dump 完清 NVS），
结果打印那一刻如果串口没连着，数据打进空气而 NVS 已清空，永久丢失。
改成**只在 RESET 时才清**，代价是反复进出页面会重复打印——那比丢数据强得多。

另外 `s_evidence_set_ms` 必须在清表时一起更新，否则车数会立刻显示 `0`，
而那个 0 会被读成"确实没有车"，实际只是"还没开始观察"。

### 5.17 v17：93% 的包没有名字 —— 累计表按名字聚合是错的

把车棚数据取回来后，只有 **7 台**车有名字。用户立刻说：「车棚里有很多电动车，远远大于 7」。

量化之后原因很清楚：

```
总包数 3934 = 无名 3674（93%） + 有名 260（7%）
```

最硬的证据是台铃用的那个 BandSpeed 模组（`manu=0x0020`）：

```
0x0020:  无名 350 包  +  TL_BEUOZB_7D / _DF  合计 36 包
```

同一批车，无名的包是有名的 **10 倍**。因为累计表按"名字前缀"分组，
**所有没名字的台铃车全被并进 `0x0020 (无名)` 一行 —— 10 台车变成 1 行。**

修法：累计表改成**按 MAC 聚合**（256 台 × 36B ≈ 9KB），名字只是设备的一个属性，
取"见过的第一个非空值"。**聚合是展示层的事，不该影响采样。**

导出时才按前缀聚合，输出带「台数」列——「台数 ≥2」就是判断"是不是一排同款车"的依据。

### 5.18 v18：SCAN_RSP 被自己的硬门限吃掉

改成按 MAC 记账后，还是只有 12 台车有名字。用户说那是一横排、往返走了一遍，
覆盖是完整的。

于是去查"为什么名字这么少"，发现是**我自己写的门限**：

```c
if (age < DUP_GATE_HARD_MS) return 0;      // 200ms 内一律丢
```

`SCAN_RSP` 的 `event_type` 是 **`0x04`**，它在收到 `SCAN_REQ` 后**几十毫秒**返回，
正好落在这 200ms 里面。**而设备名几乎只出现在 SCAN_RSP 里。**

实测数据：改动前 50 秒日志里 `0x04` 类型的包是 **0 个**；改动后是 **649 个**，
其中 22% 带名字。

> **教训**：门限按"时间"设的时候，要问一句"这段时间里会不会有另一种包"。
> BLE 的 ADV 和 SCAN_RSP 是两类东西，前者的间隔约束不该套到后者身上。

### 5.19 v19：前缀规则把品牌名的字母当十六进制削掉了

上一版规则是"从尾部去掉连续的 `[0-9A-F]`"，而品牌名里的 `E`、`D`、`A` 都算十六进制：

| 真名 | 上一版 | 现在 |
|---|---|---|

| `YD5729E0D2` | `Y` | `YD` |

聚合本身没错（同批车仍聚在一起），但**显示全错**，而且差点让我误判"绿源没出现"。

### 5.20 v20：判据是反的 —— "可连接"不是排除理由，而是特征

这是整晚最重要的一条。

`scan_class_is_vehicle()` 里有一句从 v4 就写下的代码：

```c
// 出现过可连接广播：有连接能力，不是 PEPS 车机。
if (connectable) return false;
```

**它把车棚里 29 台车全部排除了。**

为什么错：**靠近解锁要求手机能连上车**，所以车端必须发可连接广播（`ADV_IND`）。
"可连接"不是排除理由，恰恰是 PEPS 车的特征。

真正把车和手机分开的是**厂商数据长度**：

| | `manu_len` |
|---|---|
| 车（25 台 `mlen=0` + 4 台 `mlen=6`） | **0 ~ 6** |
| 手机 / 电脑（苹果、微软） | 20 ~ 27 |

车厂不走 SIG 标准格式，所以厂商数据要么没有、要么极短。

新判据 **`EVID_LINK_SHORT`（D）**：`可连接 + manu_len < 8`。
界面上原来 `C.APPER.VEH` 那一行改成 `C.LINK-SHT`，默认只勾它。

同时把三处重复的硬条件抽成 `vehicle_hard_ok()`——之前 `count_vehicle` /
`next_vehicle_wait_ms` / `count_vehicle_kind` 各抄了一遍，漏改一处就会出现
"总数对不上其中 M 台是苹果"的自相矛盾。

**效果（242 台室内逐包日志复算）**：

| 判据 | 命中 |
|---|---|
| 旧 B（`mlen>=8` 且不可连接） | **37 台误判** |
| 新 D（可连接 + `mlen<8` + 非手机） | **4 台** |
| 实机显示 | **3 台**（差的 1 台是 dwell 未满） |

从 33 台降到 3 台，而且性质变了：之前那 33 台全是手机电脑，现在这 3 台是"确实像车的设备"。

**三条旧判据全部实测失效**：

| 判据 | 车棚命中 | 原因 |
|---|---|---|
| A `EVID_UUID128` | **0 台** | 128 位 UUID 主要在**连接后**的 GATT 服务表里，广播包只有 31 字节 |
| B `EVID_MANU_LONG` | 真车 **0 台**、室内 **37 台** | 车是 0~6 字节，够不到 8；反而手机全中 |
| C `EVID_APPEARANCE_VEHICLE` | **0 台** | 242 台里只有 2 台填了 Appearance，都是华为私有的 `0xC703` |

顺带证伪了一条"用厂商 ID 白名单识车"的思路：**`0x0020` 不是台铃，是 BandSpeed**
——台铃用的是它的 BLE 模组。**厂商 ID 反映模组厂，不反映整车厂。**

### 5.21 v21：dwell 30 秒 → 10 秒（站着数车 vs 走路采集）

30 秒是给"站在一个地方不动数车"定的：车一直在广播，攒 30 秒很容易。

但实际用法是**拿着设备走一趟**：一台车在范围内只待 2~3 秒，横排往返两趟也就 6~10 秒。
**30 秒的门槛意味着走路采集永远数不出车。**

改成 10 秒。副作用：判据切换后的 `LOADING` 也从 30 秒变 10 秒（同一个常量）。

> **教训**：每个阈值都是在某个采集方式下定的。换了采集方式（站着→走动），
> **所有基于"时间累积"的阈值都要重新审一遍。**

### 5.23 v23：实验室里的「4 台电动车」全是打印机

用户开了 `LOG ON`，抓了 30 秒（6621 个逐包日志 / 76 台设备）。屏幕上那一行
`E-BIKE 4`，落到的恰好是这四台：

| MAC | 名字 | 厂商 ID | mlen | RSSI | 包数 | 实际是什么 |
|---|---|---|---|---|---|---|
| `70:68:71:88:C8:79` | `DELI_M2024DWs_56D0ES` | 无 | 0 | -69 | 903 | **得力标签打印机** |
| `5C:60:BA:2C:C2:07` | — | `0x0065` HP | 3 | -60 | 302 | HP 设备 |
| `F2:A6:54:58:91:6A` | — | `0x0065` HP | 3 | -88 | 60 | 同上（远处） |
| `F2:4E:A4:80:E5:DB` | — | `0x0065` HP | 3 | -89 | 31 | 同上（远处） |

**没有一台是电动车。** 打印机和 PEPS 车在这一层是**字节级同构**的：

```
可连接（ADV_IND） + 厂商数据 0~3 字节 + 无 128 位 UUID + 无 Appearance
```

`EVID_LINK_SHORT` 只能回答"它像不像车"，回答不了"它是不是车"。
实验室里任何一台走 BLE 配网的打印机、标签机、扫描枪都会落进这个桶。

**这次先暴露出来的是解析问题**：第一遍算出 0 台，因为日志里
**没有厂商数据时 `manu=` 整段被省略**，而 `manu=none` 恰恰是车的特征。
正则必须写成 `(?: manu=0x(\w+)/(\d+)B)?`，否则会漏掉 1534 行/30 秒（23%）。

> **教训**：「最像车的那个字段」在日志里的缺失形态，比它的值更容易踩到。
> 解析脚本先把"缺字段"补上，再谈统计。

**顺带查出两个手机数的问题**

1. 华为 `M-Pencil` 被判成手机（`phone=1`，274/359 包）。厂商分支手写了
   buds/watch/band/tws 四个排除词，**没调 `name_looks_like_peripheral()`**，
   而 `"pen"` 只在后者的词表里。改成统一调用——这是 `Pixel Buds`（v12）、
   `vivo TWS`（v12 后续）之后**第三次**同形态的坑。
2. `40:99:F6:15:35:31`，名字 `GACDF64SG059445`（像广汽），但厂商 ID 是
   `0x004C` 苹果、`sub=0x02`、RSSI -92~-95。**存疑**，要看原始字节。

**新增诊断**：sniff 日志末尾加 `ad=<hex>`（前 31 字节），只对
`可连接 && manu_len < 8` 的候选打印。因为 type/len/mlen/name 这些
**已记录字段已无法区分打印机和车**，只能看 AD 结构：
真车靠 `0x09`(完整名) / `0xFF`(厂商数据) / `0x16`(service data) 传车架号。

### 5.24 v24：把那 4 台的 AD 结构解出来了

给 sniff 日志加了 `ad=<hex>` 之后重抓 25 秒，四台设备的原始广播拆开是这样：

**① 得力标签打印机 `70:68:71:88:C8:79`**

```
ADV : 02 01 06                                     Flags = 0x06
      15 09 "DELI_M2024DWs_56D0ES"                 完整名（0x09）
RSP : len=0                                       空应答，什么都不给
```

**② 三台 HP 设备（`5C:60:BA:2C:C2:07` / `F2:A6:54:58:91:6A` / `F2:4E:A4:80:E5:DB`）**

```
ADV : 02 01 06                                     Flags = 0x06
      19 16 F7FD  01 443BAB18B3597BAAC62129F21F842D62 00000000 01
                    └ UUID 0xFDF7 ┘└── 16 字节标识 ──┘└ 计数 ┘
RSP : manu = 0x0065 / 1B                          HP, Inc.
```

三台的 UUID 都是 `0xFDF7`，中间 16 字节各不相同（`443BAB…` / `5C9A48…` / `AEBB C8…`），
末尾 4 字节是个计数（`00000000` / `33B46AC8` 会往前走）。

**对照：真车长什么样（我们还没有原始帧，只能从 [STAT] 反推）**

| | 得力打印机 | HP 三台 | 车棚里的车 |
|---|---|---|---|
| Flags | `06` | `06` | 未知 |
| 0x09 完整名 | **有** | 无 | 有（`YD…` / `AIMA-…` / `bdb-PKE-…`）或没有 |
| 0x16 service data | 无 | **有，UUID `0xFDF7`** | 未知 |
| 0xFF 厂商数据 | 无 | 只在 SCAN_RSP 里 1 字节 | 0~6 字节 |
| 可连接 | 是 | 是 | 是 |

也就是说：**我们手上至今没有任何一帧真车的原始广播**。车棚那几趟只存了
`[STAT]` 汇总（包数/RSSI/mlen/名字），没有逐包字节。

**这一版先做两件事**

1. **办公设备厂商黑名单**（`scan_class_is_office_equipment()`）：
   车厂不会用惠普的 company id。表里 13 个 ID 全部从 SIG 全表查出
   （HP `0x0065` / Epson `0x0040` / Canon `0x01A9` / Brother `0x0755` /
   Zebra `0x01F1` / Ricoh `0x065F` / Lexmark `0x025D` / Konica `0x018B` /
   Dell `0x041E` / Sharp `0x0381` / Fujitsu `0x02EA` / Toshiba `0x0004` /
   HPE `0x011B`）。**黑名单而不是白名单**：车厂用的是模组厂 ID
   （台铃 = BandSpeed `0x0020`），白名单列不全；而"哪些品牌不做电动车"是稳定的。
   效果：4 台 → 1 台（只剩那台得力标签机，它没有厂商 ID）。

2. **累计表记 AD 画像**（`scan_stats` v3）：每台设备记一个 AD Type 位图 +
   第一个 `0x16` 的 service UUID，`[STAT]` 多一列 `AD类型`：

```
[STAT] (无名 C m0)      14     50    -80   C      0    1 01,09,FF        <- 有完整名
[STAT] (无名 C m0)      20     60    -75   C      0    0 01,16/FDF7      <- 只有 member service
```

这样**不用接电脑**去车棚走一趟，回来就能看到真车的 AD 结构长什么样，
再决定判别式怎么写。这一步绕不过去——现在所有能调的参数都已经试过了，
剩下的信息只在原始字节里。

### 5.25 v25：三个勾选框删掉，合并成一个开关

用户问：「现在的三个选项是不是可以删了，因为第一第二个选项根本就不选」。

**可以，而且必须删。** 三条证据里两条已经被一手数据判死：

| 证据 | 车棚命中 | 室内命中 | 判定 |
|---|---|---|---|
| A `EVID_UUID128` | 0 | — | 128 位 UUID 主要在**连接后**的 GATT 表里，广播包 31 字节装不下 |
| B `EVID_MANU_LONG` | **0（真车）** | **37 台误判** | 车是 0~6 字节，永远够不到 8；反而手机全中 |
| C `EVID_APPEARANCE_VEHICLE` | 0 | 0 | 242 台里只有 2 台填 Appearance，都是华为私有值 |
| **D `EVID_LINK_SHORT`** | 有效 | 3~4 台 | 可连接 + 厂商数据 <8 字节 |

留着 A/B 不是"多一个选择"，是**多一个陷阱**：用户勾上 B，车数立刻从 3 跳到 33，
而屏幕上没有任何提示说明这是错的。一个只会让数字变错的选项，不该出现在界面上。

**改法**

```
  >> [x] E-BIKE        <- 焦点行，黄字=开、灰字=关
     RESET ALL         <- 动作行，橙字
```

- 存进 `evidence` 这个字节，只是**排除标记**，`evidence_mask` 永远不含它，

### 5.30 v30：自测发现 NVS 落盘失败 + 三台假车各有各的特征

用户开 LOG ON 后抓了 25 秒（`_refactor2.log`，862KB / 5906 个 sniff 行 / 无 WDT）。
逐包链路正常，但日志里冒出一行警告：

```
W (217782) scan_stats: 累计表落盘失败: ESP_ERR_NVS_NOT_ENOUGH_SPACE
```

#### 问题一：11KB 的累计表永远存不进 24KB 的 NVS

算一下就知道为什么必然失败：

| 项 | 值 |
|---|---|
| NVS 分区 | `0x6000` = 24 KB = **6 个数据页** |
| blob 大小 | 256 台 × 44 B + 12 ≈ **11 KB** |
| 一页能放 | IDF 的 blob 按 **4000 字节/页** 分块 → 11KB 占 **3 页** |
| `nvs_set_blob` 峰值 | 旧的 3 页还没释放就要写新的 3 页 → **6 页** |

峰值正好等于整个分区，而 WiFi 凭据、套件设置也要占页。所以**从第二次保存开始就
必然失败**，每 30 秒白写一次（还白磨一次 flash）。

修法：**先擦后写**。`nvs_erase_key()` 把旧 blob 的页标脏，GC 就能复用，峰值降到 3 页。
代价是这两步之间掉电会丢掉持久化那份（RAM 里的还在，下一次定时保存会重写）——
相比"永远写不进去"，这个代价可以接受。

> **顺带查出一个更隐蔽的事实**：合并出来的 `full.bin` 是用 `0xFF` 填充段间空隙的，
> 而空隙里正好包着 `0x9000~0x10000` —— **NVS 和 phy_init 分区**。
> 也就是说**每烧一次 full.bin 就把 NVS 清空一次**（WiFi 凭据、累计表全没）。
> 这一轮起改成"只烧 app 段"（`esptool write_flash 0x10000 app.bin`），
> 只在分区表/引导器真变了的时候才烧 full.bin。

#### 问题二：三台"假车"分别踩在三条不同的解析路径上

| MAC | 实际是什么 | 它身上的线索 | 线索位置 |
|---|---|---|---|
| `70:68:71:88:C8:79` | 得力打印机 | `Flags + 完整名 "DELI_M2024DWs_56D0ES"` | **AD 0x09 名字** |
| `C4:60:0A:4E:3B:77` | 小米系设备 | `03 03 92 FD` → UUID **0xFD92** | **UUID 列表（0x02/0x03）** |
| `F2:4E:A4:80:E5:DB` | HP 打印机 | `16 F7FD ...` → UUID **0xFDF7** | **service data（0x16）** |

第二、三条特别值得记：它们**是同一类"私有 16 位 UUID"，但落在两条完全不同的
AD 字段里**。第一版只判 `facts.svc16`（0x16 那条路径），结果 `C4:60` 照样被算成车——
`03 03 92 FD` 走的是 UUID 列表，`ad_parse` 把它记进了 `uuid16_mask`，没记进 `svc16`。

> **教训**：`0x16 service data` 和 `0x02/0x03 UUID 列表` 都承载 16 位 UUID，
> 但它们是**两个 AD 字段、两条解析路径**。判"这台设备有没有某个服务"时，
> 两条都得看，否则会漏一半。

为什么这次敢按 UUID 排除（之前一直说"打地鼠"）：**service UUID 在主广播包里，
不依赖对端回 SCAN_RSP**。而厂商 ID 恰恰是 `F2:4E` 那种"这轮不高兴就不发"的字段。
同一个 HP 打印机，21:48 那轮带 `manu=0x0065`、这轮完全不发——但**两轮都发了 `FDF7`**。

实现：新增 `EVID_EXCL_GADGET_SVC = 0x80`（第三个排除标记）、`GADGET_SVC[]` 白名单表
（只有实测确认过身份的两条，每条注明是哪台设备哪天的日志）、
`FACTS_UUID16_XIAOMI` 位。外设词表补 `deli`。

#### 验证：115 台 → 0 台

按新规则回放同一份 `_refactor2.log`：

```
设备 115 台，命中判据 11 台
排除分布: {'手机': 7, '外设/办公名': 1, '办公品牌': 1, '已知外设UUID': 2}
**E-BIKE = 0**
```

三台假车各被不同规则挡下（名字 / UUID 列表 / service data），说明排除链是**分流**的，
不是靠一条万能规则硬压。手机 7 台、HP 1 台仍由原有规则处理。

### 5.32 v32：换实验室后 6 台"电动车"逐台查明 —— 全不是车

用户换到新实验室，屏幕显示 **6 台电动车**。连抓 60 秒 + 180 秒（`_lab2.log` /
`_lab3.log`，129 台设备 / 21902 个逐包行 / 无 WDT），逐台核对：

| MAC | 真正是什么 | 决定性特征 | 处理 |
|---|---|---|---|
| `77:96:55:DC:6F:FC` | **Bose Revolve II 音箱** | UUID **0xFEBE**；名字 `LE-Bose Revolve II Sound` 只在 SCAN_RSP 里偶尔出现 | v32 排除 |
| `D0:62:2C:60:2C:3A` | **小米手表/手环** | MiBeacon `0xFE95` + Appearance **0x00C2 = Smartwatch** | v32 排除 |
| `40:99:F6:05:DB:96` | 不明 IoT（序列号名 `DFH…`、服务 `0xFFF0`、厂商 `0xFFDB`）| 无厂商名可用 | 仍计数 |
| `E4:01:EA:9E:17:BD` | **`MiCarB4EA9E17BD`**（名字直译"小米车"）| 服务 `0xFCD1`/`0xFFF1`，无厂商数据 | 仍计数 |

**"6 台"为什么是 6 而不是 4**：这几台的 RSSI 都在 **-93 ~ -97**（在楼下/隔壁），
包间隔几十秒，时有时无。180 秒窗口里稳定存在 4 台，某一时刻能凑到 6 台。
**这个数字是"远处设备是否恰好发了一包"的体现，不是"附近有 6 台车"。**

#### 顺带查出一个规范错误：`0x0300~0x03FF` 根本不是"车辆段"

`veh_rules.h` 里写着：

```c
#define APPEARANCE_VEHICLE_MIN 0x0300   // "Appearance 的车辆段（规范定义）"
#define APPEARANCE_VEHICLE_MAX 0x03FF
```

查 SIG《Assigned Numbers》的 Appearance 表，**规范里没有"车辆"这个类别**，
而 0x0300~0x03FF 这一段装的是：

| 值 | 含义 |
|---|---|
| 0x0300 | Generic Thermometer |
| 0x0340 | Generic Heart Rate Sensor |
| 0x0380 | Generic Blood Pressure |
| 0x03C0~0x03FF | Generic HID（0x03C1 键盘、0x03C2 鼠标、**0x03C7 数字笔**…）|

也就是说证据 C 非但不指向车，反而把温度计、心率带、手写笔都认成了车。
实证：本实验室两台华为 **M-Pencil 3** 的 Appearance 正是 **0x03C7**。

> 这条"证据"从 v1 起就写着"实测 0 命中"，所以一直没暴露——**0 命中掩盖了一个错误的定义**。
> 这也是为什么"实测没命中"不能当作"定义正确"的证据。

#### 改成反向用法：Appearance 用于**排除**

```c
bool veh_rules_appearance_is_gadget(uint16_t app) {
    if (app >= 0x0080 && app <= 0x008F) return true;   // 电脑/平板/Laptop
    if (app >= 0x00C0 && app <= 0x00C2) return true;   // 手表/手环
    if (app >= 0x0300 && app <= 0x03FF) return true;   // 体温计/心率/血压/HID
    if (app >= 0x0440 && app <= 0x044F) return true;   // 运动传感器
    if (app >= 0x0480 && app <= 0x048F) return true;   // 骑行传感器
    if (app >= 0x0540 && app <= 0x057F) return true;   // 各类传感器
    return false;
}
```

这条特别有用，因为手表/手环/传感器往往"**可连接 + 无厂商数据 + 无名字**"——
和电动车的广播形状**一模一样**，除了 Appearance 之外没有任何可用信息。
真车要么不填 Appearance，要么填 0x0000，填成"智能手表"的车不存在。

新增 `EVID_EXCL_APPEARANCE = 0x10`、`FACTS_UUID16_BOSE`（0xFEBE）。
**踩过一个字节序的坑**：AD 里的字节是 `BE FE`，小端读出来是 **0xFEBE** 不是 0xBEFE，
第一版写错，回放时那台音箱照样被算成车。

#### 效果

`_lab3.log` 回放：**命中判据 22 台 → 排除后 4 台 → v32 规则后 2 台**（Bose 与小米手表出局）。
剩下 `DFH…`（不明 IoT）与 `MiCar…`（名字像"小米车"）两台。

配套工具：`tools/analyze_sniff.py`（按固件语义回放，逐台给证据）、
`tools/sniff_wait.py`（先起脚本再让用户开 LOG ON，避开"连串口就复位"的坑）。

### 5.33 v33：让固件自己报出那 4 台 —— 两台是 Windows 电脑

上一轮离线回放说 2 台、屏幕显示 4 台。原因有两个，一个是方法的、一个是我的 bug。

**方法上的**：`dwell` 从设备**第一次出现**开始累计，而抓包晚于页面启动，
"早就进来、现在还在广播"的设备在日志里只显示几秒，回放会判成"在场不足 10 秒"。
所以回放天然比屏幕少。

**我的 bug（更要命）**：`tools/analyze_sniff.py` 用**一个大正则**匹配诊断行，
而固件在行尾会按情况加 `manu=0x../NB`、`appr=0x..`、`uuid128`、`uuid16=0x..`。
漏掉 `uuid128` 与 `uuid16=` 之后，**所有带 128 位 UUID 的设备整行匹配失败、
被静默丢掉**——正好包括那 3 台。于是回放 2 台、固件 4 台，差了一倍，**而且没有任何报错**。

> 修复：改成逐字段解析；开头打印"逐包行 N，解析失败 M"，**只要 M≠0 就说明解析器
> 又和固件对不上了**。同时处理了串口行尾交错（实测出现过
> `sub=0x0I (66540) scan_ble: ...`——`phone=0` 丢了、下一行的 "I" 粘上来）。

#### 固件自己报出来的 4 台

新增 `[BIKE]` 日志：LOG ON 开着时每 5 秒把**当前被计入车数的每一台**逐条打出。

```
[BIKE] 58:40:4E:EA:5B:0D rssi=-85 dwell=29.1s ev=0x09 name="云"
[BIKE] 66:DC:C8:E4:FA:23 rssi=-84 dwell=28.9s ev=0x09 name="DESKTOP-3T3N0S6"
[BIKE] 57:00:90:A0:47:AD rssi=-83 dwell=28.8s ev=0x09 name="LAPTOP-CPJ18I7O"
[BIKE] 70:A8:F6:F3:75:0E rssi=-95 dwell=21.7s ev=0x08 name=""
[BIKE] ---- 共 4 台 ----
```

| MAC | 是什么 | AD 结构 |
|---|---|---|
| `66:DC:C8:E4:FA:23` | **Windows 台式机**（机器名 `DESKTOP-3T3N0S6`）| `Flags + UUID16 0x180A + 128位UUID` |
| `57:00:90:A0:47:AD` | **Windows 笔记本**（机器名 `LAPTOP-CPJ18I7O`）| 同上 |
| `58:40:4E:EA:5B:0D` | 名字就叫 **「云」** 的设备 | `Flags + UUID16 0xFC66 + 128位UUID + 名字` |
| `70:A8:F6:F3:75:0E` | 无任何标识 | **只有 `Flags + TX Power`** |

**两台 Windows 电脑为什么会被算成车**：它们发 `Flags + 0x180A + 128位UUID`，
**可连接、无厂商数据、无 Appearance**——和电动车的广播形状完全一样。
唯一的破绽就是机器名。而外设词表里没有 `desktop` / `laptop`，于是两台都过了。

修复：`PERIPH[]` 加 `"desktop-"` / `"laptop-"`（**带连字符**，避免像 `pad`
那样误伤 touchpad/Tabata）。效果：4 → 2。

#### 剩下的 2 台

- **「云」**：`0xFC66` 服务 + 128 位 UUID，楼里还有一批同类（`[STAT]` 里 0xFC66 出现 1197 包）。很可能某款云终端/云桌面盒子，但**光看广播无法确定型号**。
- **无标识那台**：AD 里只有 `Flags + TX Power=0`，**没有任何可识别信息**。这类只能靠 RSSI 或物理排查。

### 5.34 v34：判据反转 —— 默认不是车，有正面证据才算

用户提了一句改变整个设计的意见：

> 「不需要认出它是电动车，只需要认出它不是电动车不就可以了吗」

这句话指出了前面所有版本的根本问题：**排除法是漏的**。

| | 集合大小 | 后果 |
|---|---|---|
| 「不是车」 | **无穷**（打印机、音箱、手表、电脑、云终端、电饭锅…）| 每见一款新设备补一条规则，已补 6 轮仍未收敛 |
| 「是车」 | **有限**（车厂就那么几十家）| 只要列得出来就够 |

所以 v34 把判据整体反转成 **白名单准入**：

```c
#define EVID_POSITIVE 0x20u     // 有"这是车"的直接证据

// veh_rules.c
static const char *const VEHICLE_BRANDS[] = {
    "yadea", "aima", "tailg", "luyuan", "zeeho", "byd",
    "ninebot", "segway", "soco", "sunra", "niu-",
};
```

`count_vehicle()` 现在多一行：`if ((e->evidence & EVID_POSITIVE) == 0) continue;`

名单里 **3 个是实测见过的**（都有日志可查）：

| 名字 | 是什么 |
|---|---|
| `LuYuan-Smart` | 绿源电动车 |
| `ZEEHO-22af44` | 极核（春风动力旗下电摩）|
| `BYD BLE3` | 比亚迪数字钥匙（`01,07,09`，带 128 位 UUID）|

**刻意没放 `micar`**：`MiCarB4EA9E17BD` 到底是小米汽车、滑板车还是米家设备，
目前没有证据；猜错的方向是"把非车算成车"，正是这个方案唯一害怕的错。

#### 代价必须写清楚：这个数字从「上限」变成「下限」

统计了 18 份历史日志，**设备级带名字的比例只有 4%~11%**（`_sniff7` 277 台里 17
台有名、`_lab5` 108 台里 10 台有名）。而车棚里绝大多数车不报名字。
所以白名单准入必然**少算**：室内归零（对），车棚会明显小于实际台数。

为了不丢信息，被排除在外的那些单独记一个数：

- 屏幕上：`LIVE 147  ?3  RAW 62` —— **`?3` 就是"像车但无正面证据"的台数**
- 日志里：`[BIKE]` = 确认，`[BIKE?]` = 疑似，两者不混

#### 实测（本实验室，`_lab5.log` 回放）

```

===== 确认 0 台（有车厂品牌名） / 疑似 3 台（像车但无正面证据）=====
  [疑似] 58:40:4E:EA:5B:0D rssi=-83 在场45.3s 云
```

**室内车数从 4 变成 0，且那 3 台仍然看得见。** 这就是想要的效果：
既不虚报，也不假装"附近什么都没有"。

#### 这个方案真正的维护点

不再是"每见到一款新设备补一条排除规则"，而是**走一趟车棚，把看到的名字补进
`VEHICLE_BRANDS`**。`[BIKE?]` 日志直接给出候选清单（名字 + RSSI + 在场时长），
照着补就行。名单补一次，长期有效。

### 5.35 新 UI：codex 用 esp_lcd 直绘重写了界面（评审于 10-21 中午，已处理 → §5.36）

10-21 中午，用户让 codex 把界面从 LVGL 换成**直绘**：新增 `page_radar.c` +
`ui_mini.c` + 点阵字库 `font_zh`（135 字）/ `font_digit`（60px 数字），
`main.c` 不再初始化 LVGL，旧 `demo_scan.c` 移出 CMakeLists。

我逐行看过一遍，**一行没改**。结论按严重程度排：

#### ① 必须修：单缓冲 + 异步 SPI，屏幕会串带

```c
// ui_mini.c:48
for (y = region.y; y < ...; y += BAND_LINES) {
    paint(user);                              // 先 ui_clear 再画，全写进 s_buf
    esp_lcd_panel_draw_bitmap(..., s_buf);    // 立即返回，DMA 还在读它
}
```

`bsp_display.c:166` 的 `io_cfg` 设了 `trans_queue_depth = 10`，而**全工程没有
任何 `on_color_trans_done`**（grep 过）。所以 `draw_bitmap` 只是把 buffer 地址
塞进队列就返回，下一条带的 `ui_clear()` 立刻覆盖同一个 `s_buf`。

算一下：一带 240×16×2 = **7680 字节**，80 MHz SPI ≈ **0.77 ms**；画一带通常
不到 0.5 ms。**下一带几乎必然赶在 DMA 读完之前覆盖它** → 横向条纹、上一带内容
串位、文字被切一半，帧率越高越明显。

修法二选一：给 io_cfg 配 `on_color_trans_done` + 信号量每带等完成；或双缓冲乒乓。

#### ② 功能回归：`[BIKE]` 逐台导出没搬过来

`demo_scan.c:349` 里每 5 秒调一次 `scan_ble_dump_vehicles()`，新 `page_radar.c`
**没有对应调用**。这是目前唯一能拿到**真实 dwell** 的手段（离线回放拿不到，
见 §5.33），丢了等于标定手段退回"推断"。

#### ③ 语义缺失：`vehicle_maybe` 没进界面

v34 把车数改成"默认不计"，为了不丢信息加了"疑似"计数（`vehicle_maybe`）。
新 `build_model()` 只读 `vehicle_count`，**没读 `vehicle_maybe`**。
结果：室内稳定显示 `0`，屏幕上没有任何东西提示"还有 3 台像车的"，
看起来像判据坏了。建议塞进右侧小字（`重新观察 Ns` 那一行）显示 `?3`。

#### ④ 行为变更：长按 OK = 关机进深睡

原来是"长按返回上级"。现在 `page_radar.c:362` → `radar_power_off()`
（`main.c:53`）→ 停扫描、按键脚切数字输入、武装 GPIO0 低电平唤醒、深睡。

风险两条：**误触**（这是唯一的操作页，长按手滑就关机）；**能不能叫醒**——
按键是**一个 ADC 分压网络**（三键共用 GPIO0），能不能拉到 < 0.8 V 触发数字
低电平**需要实测**。流程抄自 `demo_low_power` 应该有先例，但没现场验过。
万一起不来只能拔插 USB。

#### ⑤ 代码整洁

- `ble_radar.c`、`demo_radio.c` 在 CMakeLists 里但**零调用点**；
- `bsp_display_lvgl.c` 仍参与编译 → **LVGL 整个库还被链接**，而 `main.c` 从不
  初始化它。白占 flash/RAM，也让人误以为还有两条绘制路径；
- `demo_*.c`、`scan_gate.c` 已不在 CMake，是遗留文件。

#### ⑥ 小问题

- `s_confirm_deadline_us` 是 `int64_t`，32 位平台上跨任务读写非原子（概率极低）；
- `xTaskCreate(radar_task, ...)` 没检查返回值；
- `scan_ble_save_stats()` 在 UI 任务里**同步写 11 KB NVS**，每 30 秒卡一帧；
- `scan_ble_start()` 失败只打日志，界面停在"扫描停止 err N"，没有重试；
- 焦点在"无"时按 **UP** 第一下落到 `RESET`（危险行），靠两段确认兜着。

#### 核对过、**没**问题的部分（免得下次重查）

### 5.39 WiFi 对时上线（10-21 晚）：状态栏有了北京时间

**设计**：`wifi_time.c`——连 WiFi → SNTP（首选 `ntp.aliyun.com`）→ **立即断开**
（省电 + 把 2.4G 射频还给 BLE，避免拉低扫描占空比）；系统时钟自己走，
12 小时重对一次；未同步显示 `--:--`（暗灰）。凭证写死在
`main/wifi_cred_local.h`（**已验证 gitignore**，模板 example 文件可提交；
注意密码明文进固件 bin，个人设备可接受）。

**踩的两个坑**（都有普适价值）：

1. **SSID 不存在却报了"超时"**：第一轮连不上时日志只有一句超时。
   加了 `diag_scan()`（连之前先扫一圈 2.4G 并列出可见 AP）立刻看清：
   用户给的 "10181028" 根本不存在，真名是 `TP-LINK_1018`。
   **诊断留在固件里**，以后换场地连不上抓一次日志就行。
2. **`assoc -> run` 成功但拿不到 IP**：密码对、链路通，15 秒超时——
   根因是没调 `esp_netif_create_default_wifi_sta()`，DHCP 没有 netif 可跑。
   超时告警会把这种"缺组件"误判成"密码错"。排查顺序应该是：
   扫得见吗 → assoc 到哪一步 → GOT_IP 到了吗。

**结论**：对时成功（DHCP 192.168.1.105，SNTP 一次命中）。

### 5.40 WiFi 连接重试（10-21 傍晚，已烧录）

**排查链**（每步都有日志铁证，全程没猜）：

1. 凭证换成用户手机热点（vivo X100，`ccnu10181028`）后 3 次连接全超时。

2. 把扫描名单 12 → **24**（校园网 AP 密集，怕挤出榜外），依然没有；
3. 给 `on_wifi_event` 补了**断开原因日志**——拿到 `reason=201`

   （X100 找不到频段开关，大概率默认 5G；原因 202/15/2 才是密码错）。
   ⚠ 没有这个日志之前，"AP 不存在"和"密码错"是同一个症状（15s 静默超时）；
4. 用户确认校园网 CCNU 支持**无感知认证（MAC 绑定）**，在自服务系统绑了
   设备 MAC `4C:11:AE:2F:D8:2C`。固件改为连 `CCNU`（开放网络、空密码），
   **固件里从此不含任何密码**——连校园网账号密码都不进 bin，比存热点
   密码更安全（热点密码泄露无所谓，校园网主账号是统一身份认证）。

**本轮踩的两个新坑**：

1. **`wifi_ap_record_t rec[24]` 放栈上 = 启动就崩**。24 条约 2.5KB，
   `wifi_time` 任务栈只有 4KB，开机即 `Stack protection fault` 无限重启
   （抓到的日志一屏全是 Guru Meditation）。改 `static` 解决。
   教训：往这个任务里加局部大数组前先看栈。
2. **`CONFIG_LWIP_SNTP_MAX_SERVERS=1`**：原代码 `setservername(0, ...)` +
   `setservername(1, ...)` 看似有备用服务器，其实**第二个是空操作**。
   要换服务器只能改槽位 0。顺手改成**字面 IP `203.107.6.88`**
   （ntp.aliyun.com）绕过 DNS——portal 网络里 DNS 常被劫持/拦截。
   同时在 GOT_IP 事件里加了 IP/网关日志。

**现状（已闭环）**：连 CCNU 一次成功，DHCP 拿到 `10.160.138.199`。
之前 SNTP 超时的根因也坐实了——**portal 网络拦 DNS**：NTP 服务器从域名
改成字面 IP（`203.107.6.88`）后一次命中，日志 `对时成功：20:45（北京时间）`。

**两个使用层面的事实**（10-21 晚用户拔线冷开机验证）：

1. **板子没有 RTC 后备电池，断电即忘时间**。每次冷开机都是 `--:--`，
    要等开机这一轮对时（扫描 5s + 连接 + SNTP，顺利时 ~10s，
    重试拉满时 ~50s）走完才显示时间。"开机过一会才出时间"是设计内行为；
2. 已知缺陷：开机这轮如果**彻底失败**（3 次都没连上），下次重试要等

### 5.42 停车场车数恒 0：三道闸拦住真车（10-21 晚，codex，已烧录）

**现象**：判据反转修复（§5.37）后用户再走停车场，车数仍是 0。

**取证**（不用重跑现场）：累计表在 NVS 里，`scan_ble_start()` 时自动
`[STAT]` 导出。抓一次开机日志就看到——车全在、名字全对：
`YD`×7、绿源×4、小刀×3、爱玛×2、台铃×1、`bdb-PKE`×1、比亚迪×1，
**全部命中白名单**。问题出在名字之外的另外两道闸：

1. **RSSI 半径闸的口径错了**（主犯）：`SCAN_VEHICLE_RSSI_MIN=-70` 卡的是
   "最近 5 包**中位数**"。中位数语义是"最近一直待在 10m 内"，只适合站着
   观察；**走着采集**时，一台从旁边经过的车，最近 5 包混着靠近段和远离段，
   中位数被拉到门槛下（爱玛最强才 -74，中位数必死）。修法：换成
   **抗抖动峰值**（`rssi_peak2()`，最近 5 包第二高）——走路场景的诚实
   语义是"**曾进入** 10m"；取第二高而不是裸峰值，防单包多径尖刺。
2. **自适应短窗误伤车辆路径**（共犯）：§5.38 的 3 秒短窗（在场 ≤9 台时）
   也作用于车辆计数，而车广播周期 P90 ≈4 秒——车会周期性"掉出在场"，
   车数在 0 和 N 之间闪。修法：车辆五个函数（count/maybe/wait/kind/dump）
   固定用 `VEHICLE_WINDOW_MS = SCAN_LIVE_WINDOW_MS`；手机路径不变。
3. **诊断盲区**（让前两道闸隐身了一整天）：`[BIKE?]` 只打"过了硬条件但
   没正面证据"的，被 RSSI/时长闸拦掉的**连日志都隐身**。修法：
   `dump_vehicles` 加第二遍 `[MISS]`——报了车厂名但没算上的，逐台打印
   死在哪道闸（在场/硬条件/时长 + 中位/峰值/dwell 实测值）。

**顺手补白名单**（本趟 [STAT]）：`^ebike`（`EBIKE(24:BD)` 通用防盗器）、
`^zub`（`ZUB_bjq_` 疑似钻豹，待现场确认）。`Q_BASH_`/`GANA`/`NGNyj`
身份未确认，**宁缺毋滥，不收**。

**教训**：给"站着不动"设计的统计口径（中位数），换个使用姿势（走着）
就 silently 全错。**凡是为"防抖"设计的聚合口径，都要问一句它在运动
场景下的语义是什么。**

**待验证**：用户再走一趟停车场（开 LOG ON），预期 ~15+ 台；
`[MISS]` 会逐台解释任何"还没算上"的。

### 5.43 停车场实抓：RSSI 半径闸被证伪并拆除（10-22 上午，codex）

**方法升级**：用户带电脑去停车场，现场实时抓包 10 分钟
（`tools/现场抓包.bat` 双击即用；设备插 USB，开 LOG ON）。
不再是事后读 NVS 汇总，而是逐包 + 每 5 秒 `[BIKE]/[MISS]` 全量诊断。

**结果**：10 分钟内**看见 42 台报名字的车**（雅迪 11、爱玛 7、台铃 6、
绿源 4、小刀 4、EBIKE 2、bdb-PKE 3、极核 1、小牛 2），白名单全部命中、
dwell 全部攒够——但计数恒 0（只在最后走近一台小牛时短暂为 1）。
`[MISS]` 逐台给出死因：**全部死在 RSSI 闸**。

**标定数据（用户报距离 + 日志 RSSI）**：

| 实际距离 | 车的实测 RSSI |
|---|---|
| 2~3 米（无遮挡） | **-78 ~ -96**（单包最强也就 -78） |
| ~10 米（灌木/木板遮挡） | -82 ~ -94 |
| 贴着用户自己的小牛（唤醒爆发期） | 最强 -63，均值 -81 |

**结论：车的 BLE Beacon 发射功率太低，RSSI 圈不出半径**——2~3 米的
读数（-78~-96）比理论 10 米值（-70）还弱，同距离不同车差 30dB，
比 10m↔30m 的信号差还大。任何阈值都分不清远近。**已拆**
（`vehicle_hard_ok` 里的 RSSI 检查删除，`SCAN_VEHICLE_RSSI_MIN` 作废，
注释留在 `scan_table.h`）。手机路径的 -75 闸保留（手机发射功率正常，
§5.22 的语义不受影响）。

**意外收获：开关锁的信号特征**。用户的小牛（`NIU Link D26A`）休眠时
~0.1 包/秒；9:41 用户用 App 开关锁，车被唤醒 → **每秒 3~5 包持续
数分钟**。"广播率暴涨 + RSSI 跳强"就是"车主在旁操作"的签名，
以后做"车正在被使用"检测可以用。

**同批改动**：WiFi 对时间隔 12h → **3 分钟**（用户要求；开机失败等 12h
太久。代价：每次对时 WiFi 醒 ~5~10s，BLE 计数短暂打折 ~3-5%）。
已验证：开机 6.8s 首对（10:01），186s 后第二对（10:04），节奏正确。

**3 分钟对时引出的新 bug 及其修复（10-22 上午紧跟着发生）**：
用户发现界面每 2~3 分钟出现一次"等待 10s→1s"。机制：对时周期里
阻塞式 diag_scan + 连接握手让 BLE 断粮 ~3-5s，叠加车自身 ~4s 的
广播间隔，断档超过 dwell 重置阈值（当时误用 SCAN_LIVE_WINDOW_MS=8s），
**每次对时都把车的 dwell 清零，车永远攒不够 10s**。双修：

1. dwell 断档阈值独立为 `SCAN_DWELL_GAP_MS=20000`（比在场窗口长，
   离开的车仍由 confirmed() 的窗口剔除，dwell 只管"回来接着算"）；
2. `diag_scan` 只在首轮或连接失败后执行（它是诊断工具，不是每轮
   都需要的例行公事）。

**教训**：两个各自正确的改动（3 分钟对时、dwell 断档重置）叠在一起
产生了涌现行为。**引入周期性打断源时，要检查所有"沉默时长"类阈值
和这个周期的干涉。**

**环境备注**：车棚/宿舍区 2.4G AP 列表和实验室完全不同（`AP70014548`、
`vivo X300`、`@Ruijie-*`…），但 CCNU 全覆盖，对时在哪都能完成。

### 5.44 名字的覆盖率陷阱：休眠车不报名字（10-22 中午，codex）

**现象**：拆 RSSI 闸后再去停车场，屏幕只显示 2。实抓 5 分钟分析：
dump 里 `共 7~15 台`，但其中 **[BIKE?]（无正面证据）占 456 行，
[BIKE]（确认）只有 42 行**——大多数车没拿到名字。

**机制**（这次抓到了完整证据链）：

- 休眠的车发**短 ADV（len=13，不带名字）**，名字在 SCAN_RSP 里；
  而休眠车的 SCAN_RSP 应答率实测 **~0.2%~0.5%**（一台台铃 1172 个 ADV
  只有 2 个 SCAN_RSP）。站着看 5 分钟，大多数车的名字永远等不到；
- 醒着的车不一样：**名字直接塞在长 ADV（len=29）里**，不用 SCAN_RSP——
  用户自己的台铃在用户操作 App 期间就长这样，所以它是少数被算上的；
- 手机连上车之后，车**停广播**（连接态不广告）——用户两次开关锁期间，
  他的车在日志里反而静默了。

**修复**：POSITIVE 增加第二来源——**车规模组的厂商 ID**（短 ADV 里
恒有，不依赖名字）：`0x0020`（BandSpeed 车规模组，实抓 35 个不同 MAC、
0 误伤手机）、`0x1010`（EBIKE 通用模组，4 个 MAC）。名字白名单保留。
这是"见过的都是车"的经验名单，误伤时在注释里补反例。

**教训**：白名单准入成立的前提是"目标会自报家门"。**休眠设备不报名字**
这件事直到实抓才浮出来——之前所有车棚验证要么在走路（每台车只停几十秒，
恰好都是醒的/运气好的），要么看的是 NVS 累计表（时间拉长掩盖了应答率）。
"传感器在目标最常见状态下的行为"必须单独验证。

### 5.45 连环坑第四道：HID 服务误杀（10-22 中午，codex，已烧录）

**现象**：模组 ID 准入后屏幕只涨到 3~4（dump 里确认车 5 台）。
逐台查 [MISS]：5 台持续在线的台铃"在场✓ 时长✓ **硬条件✗**"。

**根因**：这批台铃的 SCAN_RSP 里除了名字还声明了服务
**HID(0x1812) + 电量(0x180F)**（手机靠近解锁/遥控功能用）。
`dev_phone_is_peripheral()` 的"带 HID 服务 = 外设"规则把它们标成
外设，且 peripheral 标记**黏性**——一次命中永久排除。
同型号谁能被算上取决于"它的 SCAN_RSP 有没有被收到过"——纯运气，
这解释了为什么数字又小又飘。

**修复**：`veh_rules_hard_ok()` 里外设排除加 POSITIVE 豁免
（与 §5.37 长厂商数据豁免同一哲学：**正面证据 > 排除规则**）。
手机排除保持绝对，不动。

**判据反转后的排除规则宿命记录**：排除规则是为旧世界（默认是车）
设计的；新世界（白名单准入）里它们每条的收益都值得重审——
排除只在"没报名字的设备"上有意义，对命中白名单的设备应该豁免。

**这条链全貌**（10-22 一天）：RSSI 闸 → 休眠车不报名字 →
HID 误杀。三道各自合理的闸串联，屏幕上是 0→2→3，**闸的串联性**
意味着最后一道没修完之前，前面修好的都看不见效果。

### 5.46 手机测距标定（10-22 中午，教学楼大厅实抓）

用户拿自己的 vivo X100（停在蓝牙设置页保持可发现广播）绕大厅走一圈，
逐包日志拉出 RSSI-距离标定：

| 实际距离 | 实测 RSSI |
|---|---|
| 0.5 米（贴设备） | -41 |
| ~8 米（大厅对面） | **-87** |
| 全程（数十米折返） | 不丢包，接收链路稳定 |

**结论一：手机接收半径 > 整个大厅**，物理层不构成限制。
**结论二：室内衰减远超自由空间**——0.5m→8m 自由空间理论掉 24dB
（应到 -65），实测掉 46dB。人体遮挡 + 室内多径 + 手机低功率广播
各占一份。**结论三：手机的 -75"附近"闸实际对应 ~3~4 米**，比名义的
5 米更紧（§5.22 的口径）。**已按用户拍板放宽到 -80（≈5 米，"同一房间"
语义），已烧录。**
（车的标定在 §5.43：2~3 米 = -78~-96，比手机还弱一个量级。）

## 7. 现场排查手册

### 按什么都没反应

页面每次按键打一行日志（**新 UI 的 tag 是 `radar`**，旧版是 `demo_scan`）：

```
I (12345) radar: key btn=2 ev=1 focus=1
```

| 现象 | 结论 |
|---|---|
| 完全没有 `key ...` 行 | 事件没进来 → 查 BSP 按键层 / `key_guard` |
| 有日志但 `focus` 不变 | 事件到了没作用到界面 → 查 `radar_page_key` 的分支 |
| `focus` 在变、屏幕不跟着变 | 绘制问题 → 先怀疑 §5.35 的单缓冲撕裂 |

`btn`：0=UP，1=DOWN，2=OK。`focus`：0=无焦点，1=手机采样，2=电动车采样，3=全部清零。

### 车数明显偏高 / 偏低

**先看 `[BIKE]` 和 `[BIKE?]`（LOG ON 时每 5 秒一坨）**，别猜：

```
I (12345) scan_table: [BIKE]  BYD-xx rssi=-85 dwell=29.1s ev=0x28 ... name="BYD BLE3"
I (12345) scan_table: [BIKE?] 58:40:4E:... rssi=-83 dwell=45.3s ev=0x08 ... name="云"
I (12345) scan_table: [BIKE] ---- 共 1 台 ----
```

- `[BIKE]` = 进了车数（有 `EVID_POSITIVE`，即名字命中 `VEHICLE_BRANDS[]`）
- `[BIKE?]` = **像车但没正面证据**，不进车数。**这一列就是"该往名单里补谁"**。

### `ev=` 怎么看（v34 之后的语义）

| 位 | 含义 |
|---|---|
| `0x01` | A 私有 128 位 UUID（真车见过：`BYD BLE3`）|
| `0x02` | B 厂商数据 ≥ 8 字节（真车 0 命中）|
| `0x04` | ~~C Appearance 车辆段~~ **已废弃**（规范里没有这一段）|
| `0x08` | D 可连接 + 厂商数据 < 8 字节（必要条件，不是充分条件）|
| `0x10` | 排除：Appearance 是手表/电脑/HID/传感器 |
| `0x20` | **正面证据：名字命中车厂白名单** |
| `0x40` | 排除：Fast Pair 配件 |
| `0x80` | 排除：已知外设 UUID（`FDF7` HP / `FD92` 小米 / `FEBE` Bose）|

> 例如 `ev=0x28` = D + 正面证据 = **确认是车**；`ev=0x08` = 只是形状像车。

### 串口日志格式

```
<MAC> rssi=-63 type=0x00 len=31 fp=A31C name="iPhone" | manu=0x004C/14B appr=0x0040 uuid128 uuid16=0x05 kind=apple ev=0x02 sub=0x0F phone=1 ad=02011A...
```

⚠ **行尾的诊断字段是可选的、且会随版本增减**（`manu=` / `appr=` / `uuid128=` /
`uuid16=` / `sub=` / `phone=` / `ad=`）。所以解析脚本**必须逐字段解析**，
不能用一个大正则——§5.33 就是因此静默丢掉了一整类设备。

⚠ 串口在高负载下会出现**行尾交错**（`sub=0x0I (66540) scan_ble: ...`，
`phone=0` 丢了、下一行行首的 `I` 粘上来）。解析器要容忍。

### 抓不到日志（0 字节）

打开串口这个动作本身就会复位设备（DTR 接 EN）。用 `tools/capture_log.py`，
它 open 之后立刻 `setDTR(False)`；要抓"进页面之后"的日志，用
`tools/sniff_wait.py`——**先起脚本，再让人开 LOG ON**。

2. Bash 里不要调 PS（安全校验会拦，报 "bypasses security checks"）；
3. `rm -rf` 会被高危命令校验拦住，清理临时文件一律 `rm -f` 逐个删；
4. `pyserial` 一 open 就复位设备（DTR 接 EN），读日志前必须 `setDTR(False)`。
5. **Codex 沙箱里跑 ninja 会"假死"**：进程在、CPU≈0、零输出（子进程被
   沙箱挡住）。编译/烧录一律走提权（`require_escalated`）；判断假死看
   `Get-Process ninja` 的 CPU 不涨、bin 的 mtime 不动。

# 2026-10-23：原始 BLE 帧上云（一）—— 4MB 存储分区 + 采集/封批/存储三层

## 需求与方案收敛

新需求：把雷达从"现场计数"扩展成"原始广播帧上云"的数据采集设备。
服务端契约（pulse.anend.net，别人已拿到）要点：

- `POST /api/v1/ingest`，`Bearer 设备凭据` + `X-Body-SHA256` 头；
- 封批触发三选一：**满 32 条 / 满 16KB / 最老的帧满 60 秒**（`flush_max_age_ms`）；
- 冻结字节幂等：封批时算好 SHA-256 连同 JSON 原样落盘，重试=重发同一段字节（§12.2）；
- ACK 逐字段核对（batch_id、hash、数量）通过才删本地数据；
- 断网/5xx 按 1、2、4…60 秒退避；409/410/422 隔离不重试；
- 水位背压：60% 告警、80% 停采新帧（丢新不丢旧）；
- 服务端靠"凭据的 SHA-256 → D1 查 device_nodes"认证，**设备节点要先在库里登记**
  （外部依赖：本地联调可用 wrangler 自己插测试节点，正式环境要找作者加）。

用户拍板的三条路线（和"边采边传"的初始方案不同，是有意取舍）：

1. **不用 FAT 文件，用裸分区环形记录**——本机"拔 USB 就是断电"，FAT 写文件
   中途断电会坏目录项；裸分区追加写 + 开机逐条校验，断电最多损失最后一条。
2. **WiFi 上传期间挂起 BLE 扫描**——C3 单天线共存，WiFi 常连时 BLE 占空比
   只有 30~70%，"边采边传"等于全天候丢一半帧。集中传换来的是可记录的干净
   空窗（丢多少明明白白），数据口径更准。
3. **缓冲+周期上传**（Flash 是缓冲垫），而不是攒满 4MB 才传。

## 关键测算（回答用户两个问题的数字，留着以后对账）

**4MB 能存多少**：按 48B/帧（ts4+MAC6+类型2+RSSI1+len1+AD31+对齐），
≈ **8.7 万帧**。时长取决于现场包率（本代码库实测口径）：

| 场景 | 包率 | 存满 4MB |
| --- | ---: | ---: |
| 车棚高峰 | 400~600 帧/秒 | **约 2.5~3.5 分钟** |
| 街道/办公室 | 100~200 | 7~15 分钟 |
| 安静室内 | 20~50 | 30~70 分钟 |

结论：真全量原始帧，4MB 在高峰只有几分钟——所以上传周期必须远小于它，
Flash 只是断网缓冲垫，不是仓库。（实际落盘的是 JSON 批，单帧约 140~170B，
比 48B 更费——上面的分钟数还要再打折，背压水位就是为此准备的。）

**WiFi 每次连接要多久**（wifi_time.c 实测 + 拆解）：
init 0.1~0.3s + 全信道扫描 0.3~1.5s + 认证关联 0.1~0.5s + DHCP 0.5~3s
≈ **正常 1~4 秒**；慢的是失败路径（15s×3 次重试，对时场景为等手机热点而设，
上传场景不该照搬——连不上就放弃本轮，数据反正丢不了）。
可优化到 ~1s：缓存 BSSID+信道跳过全信道扫描、DHCP 租约缓存/静态 IP、
搭 wifi_time 每 3 分钟对时的便车共用一次连接。

**上传对采集的影响**：挂起 BLE 后空窗 = 连接(~1s 优化后) + 传输
（HTTPS 实测吞吐 ~100~200KB/s，2MB 约 10~25s）。周期 15~30 分钟 →
占空损失 1~2.5%，且 `scan_ble_suspend/resume` 是毫秒级。

## 已实现（本轮代码，尚未编译验证）

三个新模块，职责切分（纯逻辑与 SDK 解耦，AGENTS.md 要求）：

| 文件 | 职责 |
| --- | --- |
| `main/raw_ring.h/.c` | 环形记录布局**纯逻辑**（host 可测）：40B 记录头（magic+len+SHA256）、追加规划、擦除扇区调度、回绕、背压判定 |
| `main/raw_store.h/.c` | 存储层胶水：esp_partition 擦写 + NVS 元数据（读指针/批次序号）+ 开机逐条校验 |
| `main/frame_batch.h/.c` | 采集 tap（NimBLE 回调只做序号+时间戳+入队）→ 64 槽静态 RAM 队列 → 封批任务（32帧/16KB/60s）→ 冻结 JSON 入库 |

关键语义，复查时别当 bug：

- **记录头 40B** = magic(4) + payload_len(4) + payload 的 SHA-256(32)。
  SHA 存在头里，上传时直接当 `X-Body-SHA256`，不用重算。
- **开机校验**：从 NVS 记的读指针逐条向后走（复刻回绕规则），第一条头不合法
  处就是数据末尾——断电写到一半的批自然被丢弃，前面的不受影响。
- **erased_upto 初始化**：write_off 扇区对齐时该扇区必须重擦（上一圈可能恰好
  写满或断电在"擦后写前"）；否则信任"正在写的扇区本圈进入时已擦"。
- **回绕判定**（raw_store_drop_oldest）：读指针后头不合法时先看 0 偏移——
  写侧回绕后记录必然从 0 开始；0 处也不合法才判损坏（清空重采，正常到不了）。
- **背压**：append 失败返回 ESP_ERR_NO_MEM → 丢整批记 `s_lost`；
  水位 60% 告警 / 80% 停采 / 回落 70% 恢复（迟滞防抖）。
- **batch_id = `<node_id>-<序号>`**，序号 NVS 持久化，断电续号；只有入库成功
  的批才消耗号（`raw_store_bump_seq` 在 append 成功后调）。
- **RAM 队列去不掉**：Flash 擦扇区几十毫秒，回调里写 Flash = 高峰期成百上千
  丢帧。64 槽 × 52B ≈ 3.3KB 静态 RAM 纯解耦，断电只损失过路的几十帧。
- **JSON 帧格式是暂定的**（`{"seq","t","a","at","et","r","ad"}` + 批头
  `{"v","batch_id","node","frames":[],"n"}`），**待服务端契约文档确认字段名后
  统一对齐**——这是上传器开工前的前置。

接线：`scan_ble` 加了 raw sink（**在所有去重门限之前**，雷达的去重逻辑不变，
雷达计数口径不受影响）；`main.c` 在 `radar_page_start()` 后调
`frame_batch_start()`；CMakeLists 加源文件 + `esp_partition`、`mbedtls`。
设备身份走 `device_cred_local.h`（gitignore + `.example.h` 模板，
同 wifi_cred_local.h 规矩；缺文件时降级 `DEVICE_NODE_ID="dev-local"`）。

## NO_MEM 根治：BLE 整体腾让

- 实测账目：堆总量 ~151KB，BLE 栈开着 free≈29KB，esp_wifi_init 要 ~50KB → 必然 NO_MEM，
  sdkconfig 瘦身（STATIC_RX 10→6、MGMT 5→2、关 WPA3/SOFTAP/ENTERPRISE）不够。
- 方案：`scan_ble_park()/unpark()`——WiFi 会话期间把 NimBLE host + 控制器整套拆除/重建
  （host 池动态分配会随 deinit 释放；计数表在静态区跨周期保留；不碰 NVS 防擦写）。
  接入 `wifi_link_acquire/release` 两条路径。park 后 free≈100KB，init 稳定通过。
- **坑 1**：`esp_bt_controller_mem_release(ESP_BT_MODE_BLE)` 之后控制器重新 init 必崩
  （r_lld_env_init 跳 0x0，Instruction access fault，实测连环重启 22 次）。
  deinit 自带的堆释放就够，mem_release 千万别加。
- **坑 2**：`esp_wifi_disconnect()` 的 DISCONNECTED 事件在 wifi 任务队列里异步送达，
  立刻 stop+deinit 会留下攥着已释放结构的 wifi 任务，BLE 恢复触发共存时在
  `ieee80211_output_do` Load access fault。修法：teardown 里 disconnect→200ms→stop→80ms→deinit。
- **坑 3**：`export.ps1` 会把 `IDF_CCACHE_ENABLE` 强制置 1，要在它之后再置 0；
  CMakeCache 里的 CCACHE_ENABLE 会被 idf.py 每次重写（`__has_include` 新增头文件
  在 ccache 下不会被感知——上次"凭据没编进去"的真相就是烧了 16:05 的旧包）。

## 2026-10-24 14:10 上传契约对齐（元宝）

   `seq_mod_n_eq_0` 口径一致。

   `items[n].report_type`）。
