# 车棚标定：拿着设备转一圈，回来取数据

这份文档解决一个问题：**怎么在不接电脑的情况下，把"走过的地方出现过哪些设备"带回来。**

## 为什么原来做不到

| 障碍 | 原因 |
|---|---|
| 扫描表 10 秒就过期 | 扫描表是滚动窗口，一台设备 10 秒没冒泡就清掉。走回车棚的路程早就超了 |
| 串口日志没接收方就丢 | `LOG ON` 的逐包日志是 `ESP_LOG` 写 UART，**没接电脑时没人读，直接丢弃**，不会缓存 |
| **拔线就是断电** | 累计表在 RAM 里，拔掉 USB 立刻清零。第一次实测就栽在这里：走到车棚转完一圈，回来插线时芯片 uptime 只有 98 秒——中间重启过，什么都没留下 |

前两条靠"累计签名表"解决，第三条靠**落盘到 NVS**解决。

## 现在怎么做

固件里加了一张 **累计签名表**（`scan_stats.c`）：不按时间过期，只按
**(厂商 ID, 设备名前缀)** 聚合，走到哪儿累加到哪儿。回来一进页面就打到串口。

### 操作步骤

1. 进 **Dev Seen** 页面（按 OK）
2. **不用开 LOG ON**，直接拿着设备走
3. 在车棚里**走一圈**，2 分钟足够（站着不动只能拿到身边那几台）
4. **离开前长按 OK 退出页面** —— 这一步会把累计表写进 Flash。
   如果忘了退出也没关系：运行中每 30 秒也会自动存一次，最多丢 30 秒。
5. 回到座位，插上 USB
6. **再进一次 Dev Seen**
7. 串口会打印类似下面这段

```
I demo_scan: 导出累计的设备签名表...
I scan_stats: ==== 累计 96 台设备（有名 14 / 无名 82），共 3934 包（丢弃 0）====
I scan_stats: 前缀             台数   包数  最强RSSI 类型 mlen 手机 样例名
I scan_stats: [STAT] bdb-PKE-          3     76     -55   C       0    0 bdb-PKE-7BCA
I scan_stats: [STAT] TL_BEUOZB_       2     36     -81   C       6    0 TL_BEUOZB_7D
I scan_stats: [STAT] LuYuan-Smart     1     37     -59   C       0    0 LuYuan-Smart
I scan_stats: [STAT] (无名)          82   3674     -45   CNO    27   31
I scan_stats: ==== 结束 ====
```

## 数据存在哪、什么时候丢

| 时刻 | 数据在哪 |
|---|---|
| 扫描中 | RAM，同时每 30 秒写一次 NVS |
| 退出页面 | 写 NVS（`scan_ble_stop` 里） |
| **拔线断电** | RAM 没了，但 NVS 里的还在 |
| 重新进页面 | 从 NVS 读回来 → 打印 → **不清 NVS** |

**为什么导出后不清 NVS**：打印那一刻如果串口没连着，数据就打在空气里了。
第一版做成了"导出即消费"，等于错过一次就永久丢失。现在改成只在按
`RESET ALL` 时才清，代价是反复进出页面会重复打印同一份，但那比丢数据强。

所以**看不到就再退一次、再进一次**，数据一直都在。

## 输出怎么读

### 先看 `(无名 ...)` 那几行

没有名字的设备会按"能不能是车"分档，这一组是判断有没有数准的**直接指标**：

| 标签 | 含义 | 室内实测 | 车棚实测 |
|---|---|---|---|
| `(无名 C m0)` | 可连接 + **完全没有厂商数据** | **1 台**（得力打印机） | **这一档就是车**，会跳到几十台 |
| `(无名 C m1-7)` | 可连接 + 短厂商数据 | 8 台 | 台铃就是 6 字节，会出现在这里 |
| `(无名 C m8+)` | 可连接 + 长厂商数据 | 21 台（18 台判成手机） | 苹果/微软为主，不是车 |
| `(无名 N)` | 只有不可连接广播 | 63 台 | PEPS 车不可能在这里，是手机/信标 |

**为什么 `C m0` 是车**：车棚实测 7 台车里 4 台 `manu_len=0`、其余 `=6`。
车厂不走 SIG 标准格式，所以厂商数据要么没有、要么很短。


| 列 | 含义 | 判读价值 |
|---|---|---|
| `前缀` | 设备名归一后的共同前缀 | **最重要的一列**。`(无名)` = 不广播名字 |
| **`台数`** | 这个前缀下有**几台不同设备**（按 MAC 数） | **判断"成排"就靠它**，≥2 才可能是同款车 |
| `包数` | 这组合计多少包 | 台数少而包数多 = 同一台在反复广播 |
| `最强RSSI` | 见过的最强信号 | -45~-70 = 就在脚边；-85 以下 = 隔着东西 |
| `类型` | `C`=可连接(0x00) `N`=不可连接(0x03) `O`=其他 | **PEPS 车必然可连接** |
| `mlen` | 厂商数据最大长度 | **车通常是 0 或 6**（不用 SIG 标准格式） |
| `手机` | 这组里有几台被判成手机 | 大于 0 说明混进了手机 |

### 三条判读规则，按可靠性排序

**1. 名字前缀成排 —— 最强证据**

```
[STAT] bdb-PKE-      3   76   -55   C   0 ...
```

**看「台数」那一列。** 室内 242 台设备里只有 2 台有名字（一台打印机、一台音箱），
而且都只有 1 台。**同一个前缀下有 ≥2 台 = 一排同型号的车。**

车棚实测：`bdb-PKE-` 3 台、`TL_BEUOZB_` 2 台，这是最硬的证据；
打印机的 `DELI_M2024DW*` 永远只有 1 台。

**2. 类型 = C（可连接）—— 次强**

新国标车必须支持靠近解锁，也就是**车端要能被手机连上**，所以是 `ADV_IND`（0x00）。
室内手机的 Continuity 广播是不可连接的（0x03）。

注意：`C,N` 同时出现说明同一个签名下混了两种广播类型，可能是手机（iOS 会轮换）。

**3. 包数多但前缀少 —— 补强**

同一台车在反复广播（PEPS 的心跳），包数会明显高于设备的数量级。

### 不要依赖 uuid128

128 位 UUID 主要出现在**连接之后**的 GATT 服务表里。广播包只有 31 字节，
车厂优先塞厂商数据。九号的 Nordic UART（`6e400001-...`，128 位）就是连接后才看得到的。
小米系广播里用的是 **16 位** `FE95`。

这一列留着是为了**排除**：`uuid128=1` 且 `C` 的设备，值得单独关注。

## 把结果发给我

只要把 `[STAT]` 那几行贴过来就行，或者直接说"抓好了"，我从 COM5 读。

我会做两件事：

1. 和室内基线（`_sniff7.log`，242 台）做**差值**，标出"车棚有、室内没有"的组
2. 用 `_fingerprint.py` 交叉验证，然后给出**可写进代码的判据**

## 前提提醒

如果车棚里全是雅迪、台铃、绿源这类传统车厂的产品，而它们在 Bluetooth SIG
连厂商 ID 都没注册，那结果可能是一堆 `manu=0x????` + `(无名)`。

**那也是有效结果**——它证明这条路走不通，比继续猜强。真到那一步，
建议把界面上的 `E-BIKE` 撤掉，别让它继续给出误导性的数字。
