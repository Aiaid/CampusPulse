## 当前首版范围（用户后续确认）

用户已确认使用 TF 卡，并进一步要求“现在先写初步固件，纯存 raw”。因此当前
实现为 [waveshare-raw](../../firmware/waveshare-raw/README.md)：被动 BLE 报告 →
预分配缓冲 → TF 分段原始文件，带 CRC、序号、单调时间、统计与终止原因。
下文的上传和推断属于后续设计，不是本版行为。四页中文界面已在0.1.1中实现并
刷入，车辆/候梯分析保持未启用。电源按键不分配采集功能，安全停止使用 USB `STOP`。

已完成一台板子的有界记录、同步停止和四页刷新试验，见
[首轮验收](../notes/waveshare-raw-first-acceptance.md)；持续负载、不同卡、
电池供电和断电恢复仍待验证。
后续0.1.3已加入只读卡文件导出与RTC锚点，按最终确认的PWR安全开关机、BOOT切页
实现按键；实际文件与容量核对见[文件审计](../notes/waveshare-raw-file-audit.md)。

用户决定从微雪板开始重新设计固件，并确认第一版优先“尽量完整保留接收到的
BLE 原始广播，上传后再分析”。这是新的设计方向，早先移植到
`firmware/epaper-collector/` 的代码和构建结果不能作为此设计的实现证明。
旧固件、现场数据、凭据与未确认上传的数据保留。

## 长期设计目标（上传后续实施）

1. 持续接收 BLE 广播，保存接收到的原始内容与接收元数据。
2. 网络正常时持续上传；网络中断时继续保存，在恢复后补传。
3. 屏幕显示实际采集、存储、网络和上传状态，方便在现场判断是否正常。
4. 明确记录软件队列溢出、存储写入失败、空间不足和上传失败。

首版不在设备上推断人数、车辆或候梯时间；这些分析以后端原始数据为基础。
raw 的采集与持久化不依赖统计窗口，也没有每窗口四条的配额。

“完整”的边界是实际进入 SDK 接收回调、且格式受支持的报告。接收范围、
射频竞争和控制器之前的丢失不能由软件队列零丢包推断；实测必须区分这两层。

## 硬件依据与待核对项

第一块目标暂按 Waveshare ESP32-S3-ePaper-1.54 V2：

- ESP32-S3-PICO-1-N8R8，8 MB Flash、8 MB PSRAM。
- 200 × 200 墨水屏、原生 USB、TF 卡槽。
- 板上有 RTC、温湿度与音频器件；首版仅启用必要外设。

依据：[微雪官方文档](https://docs.waveshare.com/ESP32-S3-ePaper-1.54)。
官方明确 V1/V2 的芯片、内存和示例不通用。实板版本、屏幕控制器、TF 接线、
供电保持逻辑和现有 Flash 布局须在驱动与刷写前核对；现有分区布局不是新设计约束。

PSRAM 用于缓冲，不具备断电持久性。用户已确认插入 TF 卡；板载 Flash
容量和擦写寿命都有限，不能承诺同等断网保存时长。

## 数据流和任务职责

```text
BLE 接收回调
    ↓ 非阻塞复制
预分配的接收缓冲
    ↓
记录打包与持久存储任务
    ↓ 已提交的不可变数据段
上传任务 → 服务端持久保存 → 应用层确认 → 回收已确认的数据段

上述任务的状态快照 → 独立显示任务 → 墨水屏
```

接收回调不做 JSON 编码、磁盘写入、网络请求或阻塞等待，也不按地址去重。
队列满时仍计数并保留可观测的缺口。初期不固定任务绑核或优先级常数，先按
ESP-IDF 驱动约束实现，再根据并发采集、写盘和 Wi-Fi 的实测确定。

内部 RAM 为驱动、DMA 和短时接收路径留出预算；PSRAM 承担较大的工作缓冲。
PSRAM 对 Flash 操作期间的可访问性与缓存限制，必须按实际调用路径验证，
不能仅因有 8 MB PSRAM 就把所有缓冲直接放到外部内存。

## 原始记录

每条记录至少包含：启动标识、单调递增的接收序号、单调时间戳、广播地址与
地址类型、RSSI、报告类型、原始 payload 长度和字节。网络校时另写时间锚点，
不重写历史接收时间，不把尚未校准的时间当成 UTC。

原始字节直接按紧凑记录保存；不为每个包重复编码十六进制 JSON。格式必须
版本化，定义长度、校验与截断/损坏处理，并能够在主机端独立解码。
具体二进制格式、校验粒度和批次大小尚未冻结。

首个驱动验收须明确传统广播、scan response、扩展广播及分片的实际支持范围。
不支持的类型要记录计数，不能静默截短为 31 字节后仍声称保存原文。
扫描是否主动、重复报告过滤与实际扫描参数作为配置和会话元数据记录；
尽量保留报告的基线应关闭重复过滤，主动扫描另行评估。

## 持久化与断网

建议使用预分配或有界的数据段，顺序追加原始记录，减少每包文件操作和元数据更新。
已写入缓冲、已持久提交、已上传和已确认必须分别计数。
断电后扫描并验证最后一个数据段，丢弃或隔离未提交尾部，不把损坏数据当作有效记录。
未达到持久提交点的 RAM/文件系统缓冲内容仍可能在掉电时丢失。

未确认的数据不被自动覆盖。空间不足时首版建议明确进入存储满状态并停止接纳
新原始记录，保留累计损失与状态；是否允许循环覆盖必须另作用户可见的配置决定。
TF 拔出、写入变慢和写盘错误要与网络错误分别显示，并支持可诊断的恢复。

存储选择已确认 TF 卡；以下保留替代方案对比：

| 方案 | 设计影响 |
| --- | --- |
| TF 卡 | 适合较长时间连续 raw；须验证卡速、尾部恢复与文件系统行为 |
| 仅板载 Flash | 适合有界短时缓存；须测容量、擦写开销、寿命与满盘行为 |

## 上传

上传独立读取已持久提交的数据段，不能长期占用采集或存储写入所需的锁。
批次由稳定标识、序号范围、字节长度和内容校验识别；重试相同内容，服务端去重。
只有约定接收端确实持久保存后的应用层确认才允许本机回收，MQTT broker 的
投递确认不足以表示数据已经持久入库。

MQTT/TLS 或其他传输方式、服务端接口以及与现有后台的兼容层仍待设计。
不为兼容旧的四条配额把新采集链重新限制回去；也不直接修改已部署的旧协议。
凭据通过受保护的配置流程提供，不写入源码。原始地址和广播内容进入私有存储。

## 屏幕与操作

墨水屏显示：采集运行/暂停、接收报告速率、软件丢失、写盘状态与剩余空间、
待上传字节、最近一次持久确认时间、网络状态及错误原因。
可保留类似 Passport 的现场诊断信息，但字段来源与刷新策略由新固件定义。
屏幕上标明快照时间，未校时显示未知；显示刷新不阻塞采集、写盘或网络。
刷新周期、按钮动作和 USB 配置流程待硬件核对后确定。

## 容量按测量确定

若记录平均大小为 S 字节、接收速率为 R 条/秒，则数据生成速率约为 R×S 字节/秒。
断网保存时长约为可用持久容量除以数据生成速率；协议、校验、索引、文件系统
和保留空间还会降低有效容量。RAM 缓冲能覆盖的写盘停顿约为缓冲容量除以
数据生成速率。

这些是预算关系，不是此板实测数值。稳定运行要求长期可用上传吞吐超过生成
速率，并为重连和重试留出余量；TF 容量不能解决长期上传低于生成速率的问题。

## 实现和验收顺序

1. 核对实板版本、存储介质、引脚与供电；冻结最小原始记录和主机解码工具。
2. BLE → 缓冲 → 持久存储：先离线上升负载，检查序号、内容、满盘和断电尾部。
3. 接入独立上传：验证持久确认、重复重试、断网补传及确认前不回收。
4. 接入墨水屏与配置：验证刷新、操作和网络切换不会造成无记录的采集缺口。
5. Wi-Fi/BLE/存储并发长测，报告可持续接收速率、积压变化、丢失和恢复边界。
6. 微雪基线稳定后，再决定向 AI Passport、T-Energy 等板移植哪些模块。

首版软件代码与主机工具已实现；其余架构仍为设计方向。软件构建和主机测试
不代表射频完整性、TF 卡容量/兼容性、持续写入能力或断电恢复已经通过实板验收。
