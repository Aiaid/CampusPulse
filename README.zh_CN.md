# CampusPulse

[English](README.md) · [体验原型](https://pulse.anend.net) · [文档索引](docs/README.md)

CampusPulse 是我们为华中师范大学（CCNU）做的校园观察地图，起点是校园蓝牙
热力图，后来结合华师已有的 GIS、电瓶车停车和候梯问题，加入了设备端的电瓶车
自动识别、候梯区蓝牙事件分析和时间回放。

## 从其他学校的蓝牙热力图说起

用蓝牙观察校园活动，已经有学校做过尝试。比如圣母大学的
[N-Distance](https://wireless.nd.edu/research/collaborative-intelligent-radio-systems-for-congested-wireless-environments/)，
通过参与者的手机位置和蓝牙相遇记录，生成校园接触热力图，用来观察哪些地方、
哪些时段接触较多。它需要参与者安装应用并携带信标。

也有更接近我们硬件方案的尝试：黑客松项目
[CrowdMap](https://devpost.com/software/crowdmap-2tqdch) 用 ESP32 扫描附近的
蓝牙广播，将统计结果上传到网页，展示随时间变化的热力图。

这些项目给了我们一个出发点：用蓝牙信号观察地点附近的活动，再把变化放到地图上。

## 结合华师的情况

华师已经有一套[官方校园 GIS](https://gis.ccnu.edu.cn/)，建筑、道路和地点都有
现成的底图。我们直接接入这张地图，把采集点和记录放到对应位置，方便按熟悉的
地点查看。

另一个考虑是电瓶车。学校在[南湖校区的安全检查报道](https://www.ccnu.edu.cn/info/1073/37372.htm)
中就提到过“难停、乱停”的问题，并提出改造、扩建停车位。对我们来说，除了看
哪里活动多，也想知道：某个停车点最近停了多少车，这个情况是什么时候看到的，
一天里又有什么变化。

电瓶车现在由设备根据蓝牙广播自动识别。固件解析车厂名称、已知车用模组的厂商
标识等信息，排除已知的手机、外设和办公设备特征，再结合持续在场情况统计车辆。
有明确车辆特征的结果和待确认设备分开，相关规则见
[设备端识别代码](firmware/ai-passport-radar/main/veh_rules.c)。

停车信息以自动识别为主，人工录入保留作补充和核对，不需要逐辆手工确认。这里
统计的是规则识别到的车辆，不是把附近所有蓝牙设备都算成电瓶车。

另一个想解决的问题是电梯等待时间。我们用电梯口的蓝牙观测，检查一批此前稳定
出现的信号是否在接近的时刻一起消失，据此自动找出可能的上梯事件，再分析候梯
情况随时间的变化。目前规则已经能输出候选事件；从这些线索估算实际等待时长，
还需要结合现场数据校准，事件确认所花的时间不能直接当作候梯时长。

我们还加了一条实时和历史共用的时间轴。采集的数据上传后，可以回看同一地点
前后的变化，确认哪些时段有记录、哪些时段缺数据。

## 体验原型

- [**现场观察**](https://pulse.anend.net/?mode=field)：跟随最近数据，拖动时间轴回看保留历史，再返回实时。
- [**模拟演示**](https://pulse.anend.net/?mode=demo)：探索教学日、周末与雨天的合成场景、活动和动画。

线上原型可能落后于当前代码。现场观察只显示上传的记录，没有数据就留空；
模拟演示用于体验界面，两边的数据分开。

现场时间轴默认显示最近 1 小时，可选 15 分钟／1 小时／24 小时。每类来源最多
返回最新 200 条，截断会明确提示，因此选择 24 小时不代表获得完整录制。真实数据
回看目前依赖在线 API，没有离线文件播放器或自动播放；旧的 `?mode=replay`
链接仍会打开同一条时间轴，停在最新保留记录。

地图只标出已核验位置的采集点，底图上的建筑不代表都有传感器。尚未定位的地点
仍可在数据选择器中查看记录。

## 后台管理与数据链路

CampusPulse 已有配套的[管理工作台](https://pulse.anend.net/admin)，用于维护
采集网络。后台页面和 API 覆盖设备接入、部署、配置与日常排查：

- **设备登记与部署**：登记设备、启停访问、轮换设备凭据、分配地点并保留部署
  历史。接入向导提供浏览器 BLE、桌面 USB 和设备自身 Wi-Fi 热点页面三种路径，
  具体取决于板子与浏览器能力；已有设备可以重新配网，无需重复登记。
- **采集策略管理**：编辑带版本的草稿，检查参数后发布不可覆盖的配置。后台区分
  期望下发版本、上传批次引用版本与设备明确 ACK 的已应用版本，发布后不会直接
  当作设备已经生效。
- **地点与工作用途**：同一地点可以同时配置活动、停车和候梯用途。已有设备修改
  地点或用途时创建新的部署与配置版本，保留历史归属，并等待设备明确确认生效。
  用途选择本身不等于对应的识别或估算算法已经接通。
- **运行诊断**：分别查看控制联系、上传接收和设备状态，包括扫描、内存、队列
  压力、存储以及丢失／失败计数。没有上报的数值保留为未知，旧启动或延迟上传的
  状态会明确标注。
- **上传内容核对**：分页查看持久化回执与数据库保存的条目；保留了请求原文时，
  服务端先核验 SHA-256，再展示原始字节。公开地图只查询汇总观测，地址汇总与
  原始广播内容需要经过认证才能查看。
- **站点与账号维护**：修改站点设置、查看操作审计，使用管理员密码或 Passkey
  登录；敏感操作需要最近一次身份验证。

![管理工作台：设备联系、配置状态与待处理事项](docs/images/admin-overview.png)

*实际本地后台界面，数据由浏览器内样例提供。设备和管理员均标有“样例”，
不代表生产设备清单或硬件验收结果。*

云端对每台设备独立认证，按其已分配策略校验上传批次，并返回可重复确认的持久
回执。窗口、地址汇总、可选原始广播和设备状态分流上传：D1 保存结构化记录与
回执，私有 R2 保存保留期内的研究载荷。相同批次重试可复用已提交回执；固件在
处理匹配的确认前保留本地待确认数据。

详细说明见[后台管理](docs/specs/admin-v1.md)、[账号安全](docs/specs/admin-auth-v1.md)
与[设备诊断](docs/design/device-diagnostics-panel.md)。

## 共用固件与板级适配

固件通过板级 adapter（`cp_board`）把采集上传流程与具体硬件分开。共用核心负责
策略控制、BLE 聚合、有界缓存、Flash 持久日志、上传与 ACK；适配层提供板型、
能力与资源上限，并接入各自的电池、按键和显示。屏幕渲染是可选能力，不负责
控制采集时序。

因此，新增板型可以复用数据契约和云端服务，同时独立处理引脚、驱动、供电与
Flash 分区。目标设备包括两台 AI Passport、两台 LILYGO T-Energy-S3 和一台
Waveshare 1.54 英寸 ESP32-S3 墨水屏板；各板都先具备采集、缓存和直接上传能力，
再增加 Passport 交互与墨水屏展示。

校内已有 Wi-Fi 基础设施，设备完成配网并能访问云端服务后，就可以通过 HTTPS
直接上传观测数据；临时断网时通过本地缓存与重试保留尚未确认的数据。

| 板型 | 可用代码与验证状态 |
| --- | --- |
| FoloToy AI Passport / ESP32-C3 | 已有板级适配与采集上传运行时；带屏／无屏、正常／诊断构建共用核心。已记录一次有界实机上传核对，更多现场验收仍待完成。 |
| LILYGO T-Energy-S3 / ESP32-S3 | 目标板型；本次核对的代码引用中尚未包含其 adapter 与构建／实机验收记录，仍需补充对应源码入口后确认支持状态。 |
| Waveshare ESP32-S3-ePaper-1.54 V2 | [S3 采集分支](https://github.com/Aiaid/CampusPulse/tree/463269d7e3bf4109cf8f3f07a7630fe7dba8be43/firmware/epaper-collector) 已有板级 adapter 与 200 × 200 SSD1681 状态卡，复用采集与 v2 上传核心。分支记录了 ESP-IDF 构建及一台板子的 PEAP／TLS、策略应用、扫描、上传 ACK 与屏幕核对；功耗测量和固定点现场验收仍待完成。该移植尚未合入 main。 |

## 当前进度

Passport 固件已有蓝牙电瓶车自动识别、配网、策略控制、BLE 聚合与缓存上传。
网页包含地图浏览、实时与历史共用时间轴、人工补充记录与独立模拟演示；管理后台
串起设备登记、接入、部署、策略发布与运行诊断，云端提供认证接收、持久回执和
私有研究存储。

较早的现场界面截图展示 BLE 汇总窗口；当前 main 还已接入紧凑车辆证据的规则候选
分类，以及基于已完成的人工候梯记录计算的历史参考。地图示意图会标明来源，图标
数量与排列用于示意；当前推断不会混入历史游标对应的记录。BLE 可见性事件仍属
实验分析，不能证明已经上梯，也不代表当前等待时间预测。证据条件、不可用状态
和校准边界见[自动观察说明](docs/specs/automatic-observations.md)。

接下来要拿设备到现场核对采集、联网和上传，再看记录是否足够支持回放。
准备步骤放在[采集清单](docs/notes/hackathon-delivery.md)，后续安排见[路线图](docs/design/ROADMAP.md)。

## 在本地运行

使用 **Node.js 24**，在仓库目录执行：

```sh
npm ci
npm run build
npm run db:migrate
cp .dev.vars.example .dev.vars
```

编辑已被忽略的 `.dev.vars`，将 `OPERATOR_TOKEN` 换成随机本地凭据。
需要管理后台初始化时，另外设置独立的 `ADMIN_TOKEN`；凭据不要进入源码或截图。

启动 API：

```sh
npm run dev:api
```

在另一个终端启动前端：

```sh
npm run dev
```

打开 [localhost:5173](http://localhost:5173/?mode=field)。Vite 将 `/api` 转发到
8787 端口的 Worker。新建本地数据库没有现场记录，可切换模拟演示体验视觉交互。
运行 `npm test` 与 `npm run build` 完成自动检查；更多配置见[开发说明](docs/notes/development.md)。

使用 Cloudflare Workers Static Assets／Workers，数据库为 D1，研究原始数据使用
