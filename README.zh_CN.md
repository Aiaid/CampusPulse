# CampusPulse

[English](README.md) · [文档索引](docs/README.md) ·
[路线图](docs/design/ROADMAP.md) · [在线原型](https://pulse.anend.net)

CampusPulse 希望在一张校园地图上，呈现地点的活动变化、电动车停车观察和最近
候梯实测。这个黑客松项目面向华中师范大学（CCNU）的校园场景，当前已完成首版
网页与人工记录流程，设备采集仍在规划中。

## 从同类探索到 CCNU 的需求

同类校园感知与地图可视化项目提供了一个出发点：把分散的观察关联到地点，让人
更容易了解校园里的活动。CampusPulse 希望在这一思路上，结合 CCNU 的具体场景
确定要收集什么、如何展示，以及哪些信息需要现场补充。

除了地点附近的活动变化，我们还希望关注电动车停车和楼内候梯。这三类问题需要
不同的观察方式：

| 场景 | 希望回答的问题 | 拟采用的信息来源 |
| --- | --- | --- |
| 地点活动 | 某个观测点附近，最近的活动是否发生变化？ | 固定节点的 BLE 观测窗口；采集尚未实现 |
| 电动车停车 | 某停车点最近一次现场观察到的车辆数量范围是多少？ | 人工停车记录；后续再研究车辆广播候选 |
| 电梯候梯 | 在哪个地点、什么时间，一次实际候梯用了多久？ | 人工记录已完成的候梯耗时 |

BLE 可见标识数量不等于人数或车辆数；一次候梯实测也不能直接当作当前等待时间
预测。项目会保留各类信息的来源和单位。

## 为什么需要时序信息

活动、停车和候梯情况都会变化。只有地点和一个数值，还不足以判断这条信息现在
是否有参考价值。每条观察还需要说明：**何时观察、来自哪里、有效到什么时候**，
并能回看最近一段时间的记录。

因此，我们希望呈现的是关联地点的时序观察：近期发生了什么、与之前有何变化、
哪些信息已经过期。没有观测的地方显示“未覆盖 / 暂无数据”，不会据此推算全校
热力，也不会用模拟数据填补现场数据的空缺。

## 在已有校园 GIS 上补充观察

CCNU 已有[官方校园 GIS](https://gis.ccnu.edu.cn/)，可以提供校园地点的空间背景。
CampusPulse 在这个基础上，把带有时间和来源的观察关联到地点，逐步补充活动、
停车和候梯信息。

当前网页已接入官方 GIS 底图。底图上的建筑不代表已经安装传感器或完成全校覆盖；
停车和候梯点位目前仍是逻辑演示地点，需要现场确认。地图接入方式与坐标边界见
[GIS 调研](docs/research/ccnu-gis.md)。

## 现在做到哪了

截至 2026-10-23，当前仓库的进度如下：

| 部分 | 当前状态 |
| --- | --- |
| 校园网页 | 已实现 GIS 底图、地点选择、详情和手机布局 |
| 人工记录 | 已实现停车数量范围、已完成候梯秒数的提交与撤销；写入需要操作员凭据 |
| 时间与来源 | 已实现人工记录的观测时间、有效期、历史查询和过期标记 |
| 模拟演示 | 已有独立、明确标注的合成数据演示；不写入现场记录 |
| 网页发布 | 已部署首版，并记录自动检查、云端发布和浏览器验证结果 |
| BLE 与硬件 | 规划为五台设备先采集、缓存、上传，再给两台 AI Passport 加交互、墨水屏加地点卡；固件与真机验收仍待完成 |
| 设备接口与研究存档 | 窗口／原始包／状态上传、节点鉴权、D1 回执、私有 R2 与研究解析已实现并部署到 Cloudflare，通过独立 demo 上传验收；真机验收待完成 |

可以访问[在线原型](https://pulse.anend.net)了解当前流程。当前前端默认
进入明确标注的“模拟演示”，展示合成数据；切换“现场观察”后，没有人工记录时
显示空状态是正常情况。提交现场
记录需要由项目管理员提供凭据；本地开发使用自行设置的本地凭据。

已部署版本的验证记录对应此前网页与人工记录流程；新增上传服务另见[本地验收与配置说明](docs/notes/backend-ingestion.md)。这些记录不代表 BLE 接收、硬件或真实校园场景已经
通过验收。接下来优先完成数据契约、单节点采集与上传，再适配并逐台验收全部五台
设备，验证多点链路，随后增加 Passport 交互与墨水屏展示。完整范围与优先级见
[路线图](docs/design/ROADMAP.md)。
